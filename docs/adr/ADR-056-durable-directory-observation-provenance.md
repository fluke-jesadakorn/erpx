# A Directory observation belongs to an explicitly selected durable source revision

Accepted for native implementation on 2026-10-27. Storage, owner source interfaces and component PostgreSQL race verification are implemented; complete admin assembly, full owner acceptance and runtime activation remain separate gates.

Persist an explicit source selection beside each actual Holding Directory Connection, with an increasing revision, current Connection version/configuration digest, a named shared provenance key and a purpose-separated HMAC of only the selected canonical private profile. A complete native observation records that exact source in its existing atomic reconciliation unit. A current observation is usable only when its source still matches the selected source and its ordinary five-minute freshness and identity timestamp remain valid. Source data grants no permission; current Account, IAM, HR, scope and owner authorization remain mandatory.

The current in-process profile generation protects a running operation but cannot establish which source produced a previously stored observation after restart. Its unkeyed whole-file SHA256 also includes passwords and unrelated profiles. Persisting it would expose a password-guessing oracle and create avoidable cross-profile invalidation. A stable per-selected-profile HMAC avoids that disclosure, but comparison alone would let differently configured replicas overwrite one another's observations. The durable, explicitly approved selection makes one revision authoritative across processes; API and worker construction never inserts or rotates that selection.

Changing only the file formatting or another profile does not change the selected canonical material. Changing a selected credential, CA text, TLS name, host policy, identity alias or selected Connection configuration requires explicit source rotation. Exact CA string bytes are conservative source material in this candidate; equivalent PEM reformatting also requires rotation. Reusing earlier material still advances the revision, so A-to-B-to-A cannot revive an old observation. Existing rows receive no observation-provenance backfill.

An API with local material or a key that does not match the approved binding reports a configuration failure and performs no provider I/O, source update or observation write. Missing observation provenance under a valid approved source requires a complete provider refresh. Ordinary authorization must compare the durable current selection and observation on all Directory-dependent paths, including noninteractive authority. A local file update alone is not a globally approved Directory policy change; explicit native admin selection is the activation boundary.

The native admin/seed application must validate an explicit candidate from the real retained profile, current Holding/Connection and keyring before proposing a source selection. Normal reviewed IAM/independent-review/fresh-MFA requirements apply to administration. Initial seed insertion requires expected absence; rotation requires the original selected revision and current Connection CAS, and appends sanitized source-change evidence in the same Holding unit. The database forbids revision rollback, wraparound, scope reassignment and source-row deletion. Disable the existing Connection to retire it. The current baseline has no connection-delete command; source retirement disables its Connection and retains its revision record.

Keyring entries are explicit, bounded 256-bit secret keys shared by authorized API/workers and retained outside the database. Missing keys never fall back. Add a new key to all intended instances before selecting it; advance each affected source revision and obtain a complete new observation before retiring its old key. A restart with the same key/material retains the same identity. Mixed deployment instances with the wrong material fail closed and cannot invalidate compatible instances. A provider outage after a source rotation keeps dependent work unavailable; a still-fresh observation from the retired source is not a fallback.

The additive Holding 1074 source tables and 1075 principal guard preserve the prior migration checksums and full 1072 People/external/invitation/legacy predicates. Native Control-platform Directory fails closed until its provenance schema is mirrored. The additive schema follows existing migration-role default privileges and introduces no broad grants, extensions or SECURITY DEFINER functions. Source changes use a sealed actual prepared candidate and required current Control/Holding policy ports, with no default policy or startup source registration. Its read-only `proposed_source()` getter exposes the exact proposed key/tag/configuration binding for mandatory review; reading it grants no authority. Initial seed must prove expected absence, and rotation must prove the original revision/Connection CAS. Component seed fixtures are explicitly disposable-only and do not establish real administrator/review/MFA acceptance. Current-caller integration and PostgreSQL race evidence are mandatory before the migration gate can close; schema application by unrelated components alone proves neither Directory behavior nor authority. This decision does not authorize runtime activation.

Development verification now includes 17 pure provenance cases and 14 actual PostgreSQL/owned-loopback cases. The final concurrent revision-CAS case synchronizes two first policy attempts after their real source reads, observes one additional native bounded Holding retry, and proves exactly one source/audit commit. No runtime retry count, deadline or production lock order was changed. A separate configured-authorizer case rejects a future observation with `DIRECTORY_SOURCE_CONFIGURATION` before provider I/O or the owner callback. These component results and 39 affected regression cases preserve the full admin and runtime gates above; they are not whole-candidate acceptance.

HMAC is the keyed construction specified by [RFC 2104](https://www.rfc-editor.org/rfc/rfc2104.html); [RFC 4231](https://www.rfc-editor.org/rfc/rfc4231.html) identifies HMAC-SHA256 and publishes independent conformance vectors. The proposed password-guessing protection depends on retaining the separate random provenance key outside a database-only disclosure; it is a design inference, not protection when both the keyring and database are disclosed. The actual same-transaction tuple fences must follow [PostgreSQL 18 locking semantics](https://www.postgresql.org/docs/18/explicit-locking.html), with real backend/wait evidence before publication rather than assuming the pure model proves locking.
