# Hospitality pilot feature rollout — 2026-09-23

> Historical report and scoped evidence. Current priorities, payroll scope and launch criteria are governed by [the production plan](../production-plan.md); remaining work below is retained as history, not a competing delivery plan.

This is an implementation slice, not a production acceptance certificate. The company-scoped rollout catalogue now distinguishes five user-facing states: Available, Setup required, Pilot, Coming Soon, and Prototype. Its API reports implementation support, company rollout, basic setup checks, the current role's module access, and formal delivery/business acceptance separately. Formal gates remain pending; the operator command cannot promote a module to general availability without them. The compact [`hospitality-evidence.generated.json`](../../src/data/hospitality-evidence.generated.json) is derived from the formal acceptance manifest, and the isolated release build rejects a stale snapshot.

Production starts with every module off. A Company organization administrator can change an approved P0 module to `pilot` or `off` through a versioned, idempotent, audited command at `POST /api/v1/holdings/{holdingSlug}/feature-catalogue`. `GET` returns the scoped catalogue without shared caching. The operator page is at `/holdings/{holdingSlug}/settings/pilot-features`. Development keeps existing workflows usable for engineering and demo work, while labeling its effective state separately from production rollout.

Production navigation exposes only rolled-out pilot apps. Work excludes sources for modules that have not been activated, so a deferred CRM adapter cannot appear as an unavailable hotel-pilot source. The authenticated request boundary denies new commands to unactivated and future module routes; authorized GET reads remain available for historical records. POS and PMS owner commands also check company rollout, including direct service/worker invocation. Restaurant room-charge reversal remains available for correcting a previously charged bill when POS rollout is off.

The assistant's evidence adapter also checks the company rollout before preparing a production prompt. It refuses PMS, POS, purchasing, inventory, Finance, people, operations, collaboration, learning and future-project contexts when their owning module is off; sales views and advanced Finance remain outside the P0 cut. This applies to both new answers and revalidation of saved answers, so a rollout change hides stale AI context. The isolated assistant suite passed eight tests, including deferred-context rejection and a rolled-out POS context.
The server checks the fixed P0 allowlist as well as the rollout row, so an accidental `pilot` row for a future module cannot enable its command route or assistant context. Future releases must explicitly revise that allowlist after their own acceptance.

Direct production entry screens now read the effective company catalogue and show a labelled Coming Soon or Prototype page for disabled modules, future Sales views, and Advanced Finance. The page links to the searchable future-feature catalogue. Scoped navigation works for holding and branch paths. Existing POS sale, PMS folio/document, and other record-detail links remain readable to authorized users for audit; write APIs remain gated. This page treatment is verified by path/state tests and an isolated production build, with authenticated production-browser acceptance still pending.

The production entry cut now also handles Commerce's default Sales view and unknown view parameters, plus purchasing, inventory, Finance, Operations and People list screens. Without this, a direct Commerce URL could render future Sales controls even though Sales was absent from the pilot navigation. The cut continues to leave authorized historical detail URLs readable. The mixed supplier/customer party list still needs a supplier-focused production presentation; its customer mutation commands are already denied by the Sales gate.

Deferred queue rows require operator review before a later release enables delivery, so stale customer emails cannot be sent without a fresh release decision. Company-specific gates for every remaining scheduled domain worker are still pending.

The Commerce route checks purchase/supplier and stock commands against their respective rollouts, while sales/customer commands require a separate Sales rollout. That Sales rollout cannot be activated as a P0 pilot module.
