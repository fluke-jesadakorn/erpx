ERPX Sales customer delivery notifications — automated, worker and public-browser evidence
Observed: 2026-09-21 (Asia/Bangkok)
Environment: local PostgreSQL simulation exposed through https://erpx.jesadakorn.com

Delivered behavior
- A company Finance/Sales manager configures the delivery adapter as disabled, sandbox or Resend with optimistic version checks, idempotency, audit and outbox history.
- A sales user queues one notification per fulfilled delivery. The message snapshots the order, delivery, customer, recipient and operator note so provider retries cannot rewrite history.
- Queueing requires a verified customer email, granted consent and a configured adapter. Delivery rechecks current email and consent immediately before provider access and cancels safely when either changed.
- The job worker drains due work every three seconds, reclaims expired sending leases and uses a stable provider idempotency key. Provider failures remain visible and can be retried through the order page.
- Sandbox mode never calls an external network. Resend remains a separately gated provider configuration.

Focused notification coverage
- provider required before queueing
- consent-aware immutable recipient/message snapshot
- command replay returns the same notification and duplicate queueing is rejected
- sandbox delivery records sent state without a network call
- consent revocation before delivery cancels the queued message
- Resend failure records a durable failed state; an authorized retry preserves the provider idempotency key
- notification history cannot be deleted
