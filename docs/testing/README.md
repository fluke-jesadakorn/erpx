## Owner isolation and selection

The [service boundary contract](../contracts/next/service-boundaries.md) describes semantic ports and shared transactions. The [service registry](../../src/server/modules/ownership.json) maps production source owners; the [suite manifest](../../tests/catalogue/suite-manifest.json) maps every executable test to its lane, affected modules, fixture profile and jobs/scanner prerequisites. Discovery rejects an unregistered, duplicate or missing test. The module list must match all 33 registry entries. An explicit selection with an unknown name, wrong lane or excluded file fails before execution.

```bash
bun run test                              # unit only
bun run test --module=people_payroll      # unit only
bun run test:dev --base=<verified-sha>    # affected native tests; full impact falls back to unit
bun run test:unit --module=people_payroll
bun run test:integration --suite=people_payroll.expense.integration
bun run test:e2e --module=people_payroll --list
bun run test:journeys --list
bun run test:e2e --module=people_payroll --case-order=reverse
bun run test:impact --base=<verified-sha> --list
bun run test:full
```

`bun run test` and module-only selections default to unit. Explicit files or suites retain their catalogue unit/integration lane, including mixed selections; explicit lane commands reject wrong-lane files and suites. `demo:verify` runs the purchase-to-payment integration workflow.

`test:dev --base=<verified-sha>` uses the same base/head impact mapping as `test:impact`. Affected changes run the related unit/integration suites. Full-impact changes run unit only; documentation-only changes run no tests. `--list --json` previews the development selection and every deferred internal suite. Execution writes a private receipt with `scope: development`, `acceptance: false`, selected suites, deferred suite/check commands and source fingerprints under `.scratch/dev/test-suites/development/`. It never invokes or claims full acceptance. Run the reported checks or `bun run test:full` intentionally; `test:impact`, CI and full acceptance retain their existing coverage and failure rules.

`test:full` builds and verifies its own isolated release by default. To prepare Product Host and Forms plan arms against one exact release, build first, create the private arms for that canonical release directory, then set `ERPX_TEST_FULL_RELEASE_DIR` to its absolute `.runtime/releases/<id>` path when running `test:full`. The runner rejects the mutable `latest` alias, checks the runtime fingerprint and release-file manifest, and hashes every compiled artifact before using that release. This keeps the separately scoped Product Host and Forms plans bound to the release the full run exercises.

Unit tests have no PostgreSQL setup. Integration and contract tests use the guarded local administrator and disposable databases. Browser lanes prepare their own fixture profile; every executed case receives fresh databases/files and normal sign-in/assignment selection. Module E2E and journeys run sequentially on 3102; UAT uses 3104 and the full runner verifies its compiled candidate with scanner/jobs. Sandbox/live-provider checks require explicit `test:provider` selection and their prerequisites; the internal full receipt does not attest to live providers.

Module E2E and journeys normally exercise a disposable development simulation of the frozen source. UAT exercises the compiled isolated release. The explicitly declared `pms.booking-payment-recovery.e2e` exception requires an owned compiled release on 3104, jobs and scanner; run it with `bun scripts/testing/browser-runner.ts e2e --suite=pms.booking-payment-recovery.e2e --release-dir=<owned-candidate>`. Its fictional provider transport refuses ordinary environments/live keys, and checkout navigation is intercepted locally. It is internal engineering evidence, separate from real provider acceptance. Passing a release directory does not otherwise change the 3102 lanes into compiled-release execution. Drawer tests open the real disclosure and scope inputs to its named dialog. The rapid-interaction case uses the existing inline task editor for the paused-JavaScript submit guard, then retains its Project creation and persistence proof through the normal Project drawer.

Impact selection follows ownership and reverse imports in both base and head, including deleted and renamed files. Missing mapping, IAM, transaction/runtime/migration or shared-harness changes select full regression. A focused pass does not replace a full-catalogue receipt. `development` candidate CI uses complete coverage with independently isolated browser shards; aggregation rejects missing/duplicate cases, divergent fingerprints and required skips/retries. Device-specific layout cases have explicit project requirements and written reasons; ordinary business cases remain required on desktop and mobile.

Full regression and each CI browser shard require two separate acceptance passes of every assigned browser identity: forward, then reverse across suites, projects and cases. Between passes, an explicitly declared harness fault occurs after a fresh case reaches readiness and before Playwright executes. Its retained failed receipt must prove successful cleanup; the reverse pass then restarts on the same frozen candidate. This probe provides failure recovery evidence and never counts as a passed business case. Repeated identities count once toward catalogue coverage. Missing repeats, reused run IDs, interrupted runs, changed fingerprints or incomplete cleanup reject isolation acceptance. A focused `--case-order=reverse` run alone does not establish full repetition evidence.

`test:full` writes its own run-specific `kind: "full-regression"` receipt with candidate SHA, runtime and verification fingerprints, required phase results, exact test identities and the compiled release ID plus manifest hash. The product-migration importer can bind this receipt for exact native cases mapped to a reviewed owner workflow without using the fixed `.scratch/dev/test-suites/ci/native.json` path. This does not change CI aggregation rules or provide the raw same-release browser witnesses required for a verified product-migration receipt; 133 owner workflows have browser cases in the engineering-scenario map, and Assets has a separate four-case witness, so 134 owner workflows are mapped for import and the remaining 53 need browser mappings. The 20 shared/public and Work workflows have 20 native mappings and 11 browser mappings; nine browser maps remain pending. These mappings identify eligible witnesses, not passed acceptance.

Private logs, fixture credentials and traces stay under ignored `.scratch/dev/test-suites/`. Manual screenshots use the shared case helper to keep their original capture points and basenames in each case's private output, and attach the captured PNGs to its report. Receipts retain source/verification fingerprints, actual case identities, exclusions and cleanup results before deleting owned cohorts. A failed preparation, assertion or cleanup never produces a passing receipt. Existing dated evidence remains unchanged.

Native and browser runners compare the exact runner/file/title/project identities against the retained capability, gate, Legal UAT and attachment-owner registers, the [current candidate requirements](../../tests/catalogue/required-cases.json), and the independently retained [module E2E and journey baseline](../../tests/catalogue/required-browser-cases.json). The browser baseline records eligible original identities and their explicit device exclusions; definition collection is not execution acceptance. These registers are not regenerated from a candidate's discovery during acceptance. Removing or renaming a required case fails even when the remaining discovered tests pass. Focused file/name selections check the registered identities in that selection; full and CI aggregation require all internal registered cases and retain native per-case results. Additional discovered cases may run, while an unrelated provider case is required only when its provider lane is explicitly selected.

UAT route-matrix identities additionally derive from the retained route inventory and an independent actor/scope policy, rather than the test file's discovered loops. Browser collection, full results and CI aggregation reject a missing actor category, scope loop or viewport identity; the unchanged source-inventory case checks exact source/route membership and source bytes.
