# Native Workflow command ledger

This component supplies command receipts, fingerprints, audit and outbox effects under [ADR-052](../../adr/ADR-052-rust-backend-and-domain-aligned-frontend.md). It is not complete Workflow owner migration or an activated HTTP backend. The [owner register](../../status/rust-backend-migration.json) keeps routing, SSR, jobs and remaining owner behavior pending.

## Ownership and transaction contract

`PgCommandLedger` borrows the caller's PostgreSQL connection and requires an existing `SERIALIZABLE` transaction. It cannot open a pool connection, commit, retry or call providers. Production composition supplies mandatory current Identity authorization and owner policy through `PgCommandAuthority`, plus mandatory source locking, effects and final retention through `PgOwnerCommandEffects`. There are no permissive defaults. `CommandActor` is adapter data with no request deserialization or grant semantics.

The composition root must acquire its complete owner/Identity utility lock bundle before its first data snapshot. Taking source locks later cannot refresh an old serializable snapshot. The ledger serializes each command key with a transaction advisory lock, checks current personal authority, and compares the complete request fingerprint before selecting historical replay policy. A successful replay returns the committed result without owner preparation or repeated owner, audit or outbox effects; it still requires current personal authorization. The explicit `replay` inspection uses the same protected request/source/authority path and returns `None` for a missing receipt. It does not grant a purchase purpose or authorize a new command; the caller retains the enclosing transaction and must execute current policy for any subsequent new work. An expired purchase's history purpose cannot authorize a new command.

`WorkflowRequest` contains only key, operation, record identity and input. The separate `WorkflowOutput` is produced by mandatory owner `prepare` only after exact receipt lookup returns absent and current NewWork policy passes. Preparation may read current owner facts and retain local guard data; it must not mutate canonical business rows or call providers. Its result version is checked and current personal/command policy is verified again before inserting the complete result receipt and applying canonical owner effects. This keeps a committed command replayable when its record has since moved to a state that cannot prepare the same new command again. Audit and outbox records use the same connection. Owner final retention, command policy revalidation, assertion cleanup and unchanged current authority must all succeed before the enclosing unit commits. Errors must propagate to that enclosing unit; catching an error and committing partial effects is unsupported. External effects belong in durable jobs/outbox consumers.

Concurrent conflicting insertion against an older snapshot retains PostgreSQL's real `40001`; the enclosing unit must rerun the entire operation with fresh source reads. The no-op conflict clause is safe only with the enforced serializable isolation. A regression observes two actual PostgreSQL backends waiting on the command lock, then verifies `40001` and a fresh whole-unit replay with one owner effect, receipt, audit and outbox row.

## Retained record origin

The public `record_origin` adapter supplies positive durable provenance for a closed owner inspector. A journal label is insufficient: the original create API accepts a caller-supplied source type. `RecordOriginRequest` instead names the exact command key, operation, record, original creator and Company. The reader bounds persisted text in SQL, requires a valid 64-character lowercase request hash and saved Company identity, and returns an opaque `PgRecordOrigin` only for a matching receipt. The hash is not a recovered original input or a signature over the current record; it proves neither immutable source fields nor current authority. Each owner must check its exact retained result shape and closed current source independently. Missing or unsupported legacy authority cannot establish this positive source.

Call `lock_record_origin_sources` with the complete source utility bundle before the first snapshot. Its table `ROW SHARE` lock permits ordinary receipt writers. A matching receipt is retained with `FOR SHARE`, so a conflicting concurrent source update must complete before admission or wait until the owner unit ends. A genuinely older serializable snapshot receives the real serialization failure and must restart its whole enclosing unit. These behaviors follow [PostgreSQL transaction isolation](https://www.postgresql.org/docs/18/transaction-iso.html). An absent receipt never authorizes work and needs no successful absence-based grant.

The proof has private fields and no deserialization or cloning. Final `verify_record_origin` requires the identical receipt bytes on the original database/postmaster lifetime, backend and full transaction ID, using [PostgreSQL session/transaction identity functions](https://www.postgresql.org/docs/18/functions-info.html). Returning an identical receipt from a later transaction cannot revive an old proof. Same-unit metadata changes also fail final retention. The proof grants no permission, purchase, release eligibility, or request replay; current Identity, Commercial and owner policy remain mandatory.

## Persisted JavaScript compatibility

`CommandJson` normalizes bounded JSON using captured ECMAScript behavior rather than unordered object serialization. Input and output are limited to 2 MiB and nesting to 128. The PostgreSQL replay reader also checks persisted text byte lengths inside SQL and transfers only capped fields; an oversized old result or authority returns a typed unavailable failure before parsing, owner preparation or effects. This avoids allocating an arbitrary retained TEXT value merely to reject it afterward. The implementation preserves insertion order, integer property enumeration, duplicate-key replacement position, IEEE-754 numbers, negative zero, nonfinite overflow normalization and escaped lone UTF-16 surrogates. The pure Rust `ryu-js` formatter supplies ECMAScript number formatting. Lone surrogate compatibility for receipt bytes does not authorize those values in a database or business DTO.

Fingerprints preserve the original literal actor field order and omitted-versus-null values. IAM metadata is retained in receipt/audit/outbox data but does not participate in the request hash. Original assignment scope is distinct from the selected Company/Branch. A saved legacy receipt may reconstruct its historical three-field work authority only after matching its operation, actor, record and current scope facts. Saved authority never replaces current Identity authorization.

The narrow Guest Account compatibility bridge retains old persisted spellings and the captured JavaScript property-lookup quirks as data only. It creates no prototypes, functions or legacy routes. Exact oracle files are explicitly excluded from the terminology guard so they can prove historical compatibility; new business vocabulary remains subject to that guard.

The source-bound development oracle imports unchanged B0 TypeScript on pinned Node 26.11.1. Its corpus contains 47 JSON normalization cases, 227 fingerprints, 54 bidirectional data conversions, 15 operation mappings and 24 historical replay cases. Generation supports `--check`; it is development verification, not a Node dependency of the native runtime. Synthetic test authority ports are labelled explicitly. Actual Legal/Identity composition has separate PostgreSQL integration tests and remains unmounted pending full migration.


## UTF-16 receipt identity and UTF-8 storage

`CommandJson::string_utf8_storage` exposes only a string's PostgreSQL UTF-8 representation. A valid surrogate pair remains its Unicode scalar; an isolated UTF-16 unit becomes replacement text in storage, matching the pinned Node UTF-8 conversion. The original normalized `CommandJson` remains unchanged for receipt hashing. Distinct lone units can have the same storage text and must still have different command fingerprints. Non-string values return no string view. The Finance normalizer owns the sealed connection between its exact command JSON and typed storage input; this helper does not accept a caller-provided hash override.

Owner wire adapters can inspect UTF-16 string units and ordered array elements and rebuild a bounded normalized string through the same codec. This preserves lone-unit distinctions while implementing the original owner's trim/schema rules. The UTF-8 storage view remains separate; neither these data helpers nor a normalized body can construct current authority or bypass the command ledger.
