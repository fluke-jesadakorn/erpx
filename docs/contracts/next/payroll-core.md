# Payroll core and controlled corrections

Payroll is a Company-scoped, versioned workflow that snapshots approved compensation, approved time, overtime handoffs, released Benefits inputs and approved advance repayments. Gross-pay previews remain available with their explicit fixture label. A production-mode Thai run requires the recognized, independently activated `thai-payroll-v1` source-dated rule pack and an independently approved employee allowance, Section 33 eligibility and opening-YTD profile. Readiness checks the adapter and its retained evidence rather than blocking every production-mode run. [Primary source review](../../research/thai-payroll-rules-2026-10-02.md) records the reviewed 2026 rules and explicit unsupported statutory categories.

## Corrections after posting and payment

`POST /api/v1/holdings/{holdingSlug}/people/payroll/runs/{originalRunId}/adjustments` creates a separate production run for one employee in the original posted run. It requires the original expected version, employee item, current reviewed country pack, later payment date, stable source reference, independently reviewable reason/evidence and nonnegative minor-unit arrears. Approved omitted OT must belong to the original work period and cannot already occur in the original snapshot or another active adjustment. The original posted row, employee result, GL, issued slip, review CSV and bank instructions remain immutable.

`POST .../people/payroll/runs/{adjustmentRunId}/adjustment-edit` appends a draft source revision with expected version. Prior revisions and released OT claims remain retained. Safe draft cancellation releases active source claims for an exact retry. Calculate, submit, independent review, Finance post, own-employee payslip and independent bank settlement use the existing run owner commands. The adapter pays no ordinary salary twice, uses actual posted prior YTD once, and charges only incremental tax/SSO. Negative amounts use the reviewed recovery owner; they cannot create a negative bank instruction or an automatic statutory refund.

The posted run's **Posted payroll corrections** panel exposes creation, draft editing, retained source revisions, and source-linked child runs. Current Company authority, exact source versions, idempotency, audit and outbox commit with each owner command. Migration `0934_payroll_posted_adjustments.sql` preserves immutable posted items and source claims.

## Employee agreement and net recovery

`POST .../people/payroll/runs/{originalRunId}/recoveries` requests recovery against a fully posted and bank-settled employee item, bounded by its original net and any existing active recovery claims. It requires a stable source reference, evidence, and a monthly schedule within the retained dated policy. The employee's own `POST .../people/payroll/recoveries/{id}/consent` records consent or decline. Consent requires the current employee legal name and explicit acknowledgement of the exact source, amount, schedule and limits; the immutable generated HTML agreement and SHA-256 remain downloadable with own-employee/current-grant scope. It is an internal recorded agreement, without external signing certification.

An independent holder of `payroll.approve` uses `POST .../recoveries/{id}/review` to record reviewed permissibility and its lawful-basis evidence, or reject the proposal. Consent alone cannot approve a deduction category. The requester can cancel before recognition, retaining the agreement and history. A separate Finance approver uses `POST .../recoveries/{id}/recognize` to post the reviewed THB-functional receivable and release the exact approved advance-installment handoff. Finance recognition cannot precede consent or release a schedule already posted by ordinary payroll. Income-tax/SSO adjustments are separately reviewed; original statutory YTD is retained.

Later payroll calculates each approved recovery installment with conservative individual 10% and combined nonstatutory 20% limits against actual gross wages. Native posting row-locks the source and commits an immutable consumption receipt, collected status and receivable-credit GL together. Each receipt identifies the original installment version, employee item, posting journal and amount; a terminal collected installment cannot be reopened or collected twice. The parent deduction schedule closes after all installments are collected. Migration `0935_payroll_recovery_handoffs.sql` enforces the source/agreement lifecycle and posting receipt; it does not assign fabricated receipts to historical records.

`GET .../people/payroll/recoveries` and `GET .../recoveries/{id}/agreement` power the real Payroll recoveries page. Employees see their own agreements; Company Payroll/Finance owners see authorized workflow sources. Every command and replay rechecks current authority.

Each Position may have a versioned monthly pay default with pay group and currency. People and Organization show its amount only to authorized compensation readers. When HR accepts a recommendation for an Engagement without compensation history, the system creates a draft Compensation Revision; a different person must approve it. Existing approved Compensation Revisions remain the sole pay basis for Payroll. A Position default change does not change current pay or rewrite past revisions. Acme development amounts are fictional USD fixtures, not certified compensation or Thai statutory rules.

`POST /api/v1/holdings/{holdingSlug}/people/organization/positions/{positionId}/default-pay` creates the next version using a matching active monthly pay group, amount in minor units, and expected version. People directory and lifecycle placement requests carry explicit `acceptRecommendedPay`; no pay amount is returned to a caller without compensation permission.

Monthly pay groups aggregate salaried, daily and hourly employment. Daily rates, standard daily hours and hourly rates are independently approved Compensation Revisions; approved time determines daily/hourly wages and OT. Earning components explicitly classify recurring service charge, occasional bonus/OT and exempt income, together with their Section 33 wage treatment. The adapter retains source revisions and deterministic income-tax/SSO calculations. Later monthly and December/final runs use actual prior posted statutory items once, plus reviewed opening YTD. Source versions and counts are rechecked during review and posting.

Controlled Finance GL posting and payment-batch preparation, independent approval, retained export and exact bank-result confirmation exist for approved runs. Statutory-enabled and production-environment actions verify retained adapter calculations. A generic bank CSV and declared synthetic bank evidence prove the interface and settlement controls; they do not execute a bank transfer or certify a provider/filing. [The active engineering plan](../../production-plan.md) tracks completion separately from external certification and deployment.

## Review and correction lifecycle

The creator or named preparer with current Company-level `payroll.prepare` authority can cancel an unsubmitted ordinary draft, calculating draft, failed calculation or preview using `POST /api/v1/holdings/{holdingSlug}/people/payroll/runs/{runId}/cancel`. The command requires the expected run version, a reason and an idempotency key. The detail page exposes the same action through **Cancel payroll draft**. A system-created scheduled draft belongs to its named preparer for this action.

Cancellation increments the run version and retains the exact original row in an immutable owner receipt together with audit, outbox and flow history in one transaction. Calculated items and issued review-export bytes remain unchanged and downloadable. Current selected assignment, principal and published permission are rechecked before replay and at commit; concurrent calculation or cancellation cannot bypass the original source version. Cancelled periods cease reserving the pay group, allowing an exact-period replacement without rewriting or deleting the cancelled record. Submitted, independently approved, posted and final-pay runs cannot use this path; the database also rejects a cancellation when a posting, payslip, payroll journal or payment batch exists. Migration `0933_payroll_draft_cancellation.sql` enforces retained-source equality, terminal cancellation and the immutable receipt at commit.

1. A holder of `payroll.prepare` creates and calculates the run.
2. The named independent holder of `payroll.approve` approves the current preview. The input digest and review export identify the exact revision reviewed.
3. A preparer can request a correction only against the current approved version. The request snapshots the run version, revision, input digest, totals and reason.
4. A different person with active Company-level `payroll.approve` authority approves or rejects the request. The requester can cancel a pending request. Stale decisions fail if the run evidence changed.
5. Approval returns the run to `calculating`, clears its prior approver and increments its version. Recalculation creates a new revision; previous exports remain downloadable and unchanged.

Only one correction can be pending for a run. Request and decision commands require an idempotency key and expected version. Correction events and issued review-export rows, object keys and SHA256 digests are immutable; migration `0928_payroll_review_exports_immutable.sql` rejects export UPDATE/DELETE without changing historical bytes. Inbox visibility is recalculated from the recipient's current Company-level payroll authority, so revocation removes access to the target even if an old notification remains stored. Corrections of an approved, unposted run produce a new calculation revision; this command never rewrites a posted payroll or its GL.

## Routes

| Route | Command |
| --- | --- |
| `POST /api/v1/holdings/{holdingSlug}/people/payroll/runs/{runId}/cancel` | Creator or named preparer cancels the current unsubmitted ordinary run and retains its source |
| `POST /api/v1/holdings/{holdingSlug}/people/payroll/runs/{runId}/corrections` | Request correction of the current approved run version |
| `POST /api/v1/holdings/{holdingSlug}/people/payroll/corrections/{correctionId}/decide` | Independently approve/reject, or requester-cancel, a pending correction |

The run detail at `/holdings/{holdingSlug}/people/payroll/runs/{runId}` shows correction history, source revision, reasons and role-appropriate actions.

## Final pay from retirement clearance

The assigned Payroll owner can prepare final pay directly from the retirement clearance case. The command verifies the task owner, task version, engagement pay group/currency and last working date, then creates one `final_pay` run scoped to that engagement. A recognized rule pack enables statutory final wages with reviewed actual YTD; monthly salary prorates active days against the calendar month's day count. Same-day final pay is allowed on the last work day, while ordinary monthly pay retains its requirement to follow the work period. The run links to the clearance task and retains an immutable preparation event. Independent Payroll review, Finance accrual posting, independent payment approval, retained generic export and exact bank settlement use the ordinary owner services. A second active preparation for the same task is rejected. Severance lump-sum tax and automatic refunds of overwithheld final tax require a separately reviewed rule; they fail with explicit readiness codes.

`POST /api/v1/holdings/{holdingSlug}/people/lifecycle/tasks/{taskId}/final-pay` creates the linked person-scoped preview and requires `Idempotency-Key` plus the current task version.

`GET /people/payroll/summary?month=YYYY-MM` exposes actual posted Company pay-month/currency aggregates to `payroll.read`; scoped assignments, payment-only Treasury and employees cannot read it. Detailed employee results and statutory evidence are omitted from the summary. Tests in `payroll-statutory.test.ts` exercise corrected consecutive posted months feeding December actual YTD, immutable review exports, and assigned final pay through balanced accrual, matched bank settlement, zero net payable and completed clearance.

## Payroll advances

Employees with `self.requests` can request an advance for their own active pay-group engagement; Payroll preparation roles can submit one for an eligible employee. The request records amount, currency, reason, first deduction period and one-to-24 installments. A different Company-level `payroll.approve` holder must approve or reject it, while the requester can cancel a pending request. Approval creates an immutable decision event and an exact repayment schedule whose remainder is distributed to the earliest installments.

During calculation, open or reserved repayments whose due period overlaps the run are included as deduction components and copied into the input snapshot. Each repayment is guarded by its advance and repayment version, so stale or cancelled schedules cannot silently change a reviewed preview. The advance list and request/review actions are available at `/holdings/{holdingSlug}/people/payroll/advances`; API commands are `POST /api/v1/holdings/{holdingSlug}/people/payroll/advances` and `POST /api/v1/holdings/{holdingSlug}/people/payroll/advances/{advanceId}/decide`.


## Immutable employee payslips

Posting a reviewed payroll run issues one immutable payslip per employee and run revision in the same transaction as the journal. It retains employee legal identity, original recipient account, input/result/statutory digests, exact component amounts, source journal, HTML bytes and SHA256. Idempotent posting never issues another copy; later directory or delivery changes cannot rewrite the retained slip. A historical posted run with legitimate retained input and source posting can issue missing copies through `POST /people/payroll/runs/{id}/issue-payslips`, with current Finance authority, expected version and an idempotency key.

`GET /people/payroll/payslips` defaults to the current employee's copies. `/{id}` and `/{id}/export` require the captured recipient to remain the person linked to the current user and selected active assignment; another employee, Company or revoked cached grant cannot read them. Company-level Payroll readers can review run copies through `/people/payroll/runs/{id}/payslips`. The normal `/people/payslips` and detail pages show the issued revision, source calculation, current bank-delivery state and retained download. Delivery settlement updates its separate status while the issued bytes stay unchanged. Source-dated statutory wording describes reviewed engineering calculations and separately identifies provider delivery and certification.
