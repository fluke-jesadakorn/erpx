# Native Files components

## Canonical Legal original reads

This is an implemented Files owner component under [ADR-052](../../adr/ADR-052-rust-backend-and-domain-aligned-frontend.md), not a completed Files migration or an activated download route. The [owner register](../../status/rust-backend-migration.json) and [delivery plan](../../production-plan.md) retain the remaining gates.

`erpx_server_files::public::canonical_original` exposes the native reader, storage port and explicit current-parent policy port. The reader accepts a configured Holding/Company binding and borrows the caller's existing `SERIALIZABLE` Holding connection. It does not obtain another pool connection, retry, commit, read another owner's private tables or make provider calls. Composition must retain the Control authorization lease through the complete Legal inspection and its commit.

`OriginalReadActor` contains selection facts only. It cannot authorize bytes. `PgOriginalReadPolicy::prepare` must acquire the current Legal, purchase and authority source leases in the common owner lock order before shared Files locks. `authorize` must correlate the exact current principal/selection, Legal document, canonical link, record policy, purpose, classification/audience, purchase eligibility and preservation state. It returns a bounded current-source fingerprint, not a reusable bearer grant. There is no permissive production policy implementation; the current test policy is explicitly confined to disposable test fixtures.

The Files reader requires a bound `legal_document` record link on the exact Company and Legal item/document, policy version one, restricted classification and `legal-managed` retention. The source must be available, unrevoked, undestroyed and completely scanned as the exact requested Legal MIME: PDF, PNG, JPEG or DOCX. It rejects legacy unscanned, quarantined, failed or destroyed sources and mismatched hashes, bindings or byte limits. A raw Legal `object_key` without this canonical link cannot select this reader. The full source/link/set/upload/scan snapshot participates in its opaque witness.

Table locks prevent later writes but cannot refresh an earlier PostgreSQL serializable snapshot. Tuple locks on the selected source, link, set, upload and existing scan evidence make committed conflicting updates fail with their original SQLSTATE for the outer Holding unit of work to retry. A regression establishes an owner snapshot, commits revocation from a second real backend and proves that stale bytes are not read. The current owner policy is responsible for equivalent fresh authority and preservation fences, including relevant negative predicates.

`OriginalReadWitness` has private fields and no deserialization. Revalidation requires the original query, actor, database, backend and transaction identity as well as the complete current source and policy fingerprint. A witness from a prior transaction is rejected even when the pool reuses the same backend. Successful byte reads append an access event in the caller transaction; caller rollback also rolls back that event. Legal must revalidate the witness before retaining inspection evidence and committing its surrounding workflow. Standalone denied-read audit retention remains part of the pending general Files route migration.

For work computed outside a transaction, `OriginalRead.input_identity.source_data_sha256` is a separate, deliberately constructible data digest. It binds the full canonical link/set/source/upload/scan image and exact Holding/Company/item/document/link/MIME/checksum; it excludes the transaction, current caller/authority and read access events. It is not a grant or reusable witness. Preparation commits and drops its proof before compute. Finalization must perform a fresh authorized read, remint and locally revalidate its own witness, and only then compare input identities. The same-backend regression proves that unchanged source data keeps this digest across a changed allowed authority while the old transaction witness remains unusable.

## Private local storage

`LocalOriginalStore` reads the existing native file layout: a SHA-256 directory of the logical key, bounded `current.json` manifest and immutable UUID body version. It checks manifest key, size, digest and version, then checks actual body length and SHA-256. It does not reinterpret object keys as filesystem paths or return preview bytes in place of the original.

The store opens the configured absolute root once. Relative descriptor-based opens use `O_NOFOLLOW` for the hashed directory, manifest and UUID body; only regular bounded files are accepted. Manifest reads stop at 64 KiB plus one detection byte. Body reads stop at the declared size plus one detection byte and the business ceiling is 10 MiB. A bounded semaphore remains owned by the blocking I/O task when its async caller is cancelled. Runtime permissions must keep the private root writable only by the storage service; this read-only component does not provision, upload or destroy objects.

Eight native unit cases cover exact scope/policy/lifecycle validation, compatibility with the existing manifest, tampering, limits and directory/manifest/body symlinks and the non-deserializable witness boundary. Four real PostgreSQL cases cover owner-transaction retention/rollback, current authority/source changes, invalid selections, storage integrity, same-backend transaction fencing and the earlier-snapshot revocation regression. They establish this component's behavior only. Uploads, scanning/derivatives, publications, other owner policies, preservation/destruction commands, HTTP/SSR activation and complete browser/provider acceptance remain pending.

## Portable media admission rules

The native Files domain also implements the current upload-signature hint and byte media detection rules for PDF, PNG, JPEG, WebP, HEIC/HEIF, specialized DOCX and UTF-8 CSV. A retained corpus compares 3,852 cases against the unchanged B0 TypeScript sources executed on pinned Node 26.11.1. The development generator verifies both source files against that exact commit before producing expectations. Native runtime paths do not import or execute the TypeScript oracle.

These rules classify byte signatures only. Some structural fixture containers intentionally exercise admission checks without being decoder-valid images or complete Office packages. A match is not malware clearance, successful decoding, safe preview generation, signature validity or publication authorization. The existing scanner and decoder gates must still run in their native worker migration; the thin compatibility upload hint is deliberately distinct from the stronger full-byte detector.

## Native local malware scanner

The portable `MalwareScanner` application port returns explicit clean/infected evidence or an infrastructure error. Its `ClamAvScanner` adapter sends bounded in-memory bytes to one configured absolute Unix socket using the official [ClamD INSTREAM protocol](https://docs.clamav.net/manual/Usage/ClamdProtocol.html). It never sends a client filename, document URL, filesystem scan command or environment-derived destination from request data. Definition metadata and the local daemon socket are explicit composition configuration.

Readiness requires `PING`, a ClamAV `VERSION` response and a current installed `daily.cvd`, `daily.cld`, `main.cvd` or `main.cld` modification witness. Missing or stale definitions fail closed; the default caller configuration uses a 24-hour age limit. The adapter does not download definitions or start/reconfigure the daemon. FreshClam and daemon reload remain operational responsibilities.

Chunks use 32-bit network-order lengths and a zero-length terminator. Input is limited to 10 MiB; reply records are limited to 4 KiB and require their NUL terminator. Only explicit `stream: OK` or a bounded `stream: <signature> FOUND` record produces a verdict. Empty, truncated, malformed, over-limit or daemon error replies are unavailable, never clean. Commands have a maximum five-second deadline and complete scans a maximum thirty-second deadline; the scan deadline includes admission and readiness. Cancellation drops its socket and permit. Concurrency is bounded independently of database pool size.

Five native fake-daemon cases check fragmentation/chunking, readiness evidence, infection/error parsing, missing/stale definitions, malformed reply budgets and deadline/admission cleanup. A separate explicit provider case verifies benign and standard EICAR test-signature verdicts against the existing real local daemon, sending all signature bytes in memory. It requires only the two scanner paths and no PostgreSQL or deployment credentials. Provider verification remains outside daily unit/CI selection. This adapter does not complete source scan queue claims, preview/decoder jobs, authorization, object persistence or route activation.

## Bounded native preview computation

The separate `preview-provider` feature exposes a Rust worker child using the qualified native libvips, HEIF and Poppler tools. Default Files/API builds exclude that feature. Input is bounded to 10 MiB and 40 million pixels, output to 32 MiB and a 2,400-pixel edge, and the preview deadline to 40 seconds. The trusted tool profile is verified before and after every child outcome, including a typed decoder failure. Changed tools or an exhausted deadline cannot become a content-rejection classification. The owned Runtime subprocess infrastructure retains the dedicated process group until cleanup and reap, including cancellation.

The retained [preview corpus](../../../fixtures/files/preview/README.md) contains 22 B0 cases. Three real provider tests compare the qualified Darwin worker with the retained exact output bytes; four separate held-tool fault cases cover the failure-path profile and deadline gates. These earlier checks establish the stated local component behavior only. Linux codec/ABI/font closure, distribution obligations, production image size and both CPU architectures require separate qualification. No decoder result grants a source read or publication permission.

## System scan claims and intended settlement

`public::attachment_scan` now contains the source/lease, storage and settlement components. Four policy tests, four real private-I/O ownership tests and eight disposable PostgreSQL tests pass through the common runner. They cover the intended-image/rollback gates, stale reclaim, six retries, legacy/specialized origins, transaction freshness, actual immutable-storage adoption and corruption/no-follow refusal. They are not a mounted scheduler, completed Files owner or release acceptance. The explicit development Holding/system composition and joined real provider verification described below now exercise these components together. Owner-specific preview read policies, scheduling/bootstrap activation and production/Linux qualification remain pending.

Sanitization uses the actual 60-second job lease. A current claim returns only owned source/input data; it retains no database connection or transaction proof through file I/O, malware scanning, decoding or derivative staging. Final settlement reacquires a fresh `SERIALIZABLE` source and the exact database, job, attempt, token and live deadline. A stale worker cannot change source/upload state, audit events, storage accounting or retry rows. Existing interrupted work reclaims the same attempt; only a settled scan error schedules the next attempt through six with the B0 2/4/8/16/32-second delays. Inconsistent competing open attempts fail closed and are not automatically repaired.

Accepted uploaded drafts may be sanitized before their business parent is saved. The reader proves positive managed, exact legacy-alias or specialized Files origin plus current upload/link/set/original-ledger integrity. This is Files/system authority: it adds no current Person, purchase or `created_by` permission shortcut. Uploaded-intent expiry is not the pending-intent expiry rule. The independent [effect-intent corpus](../../../fixtures/files/scan-lifecycle/README.md) retains 30 unchanged B0 algorithm cases and 322 legacy alias combinations; it is not a substitute for native SQL or provider tests.

The private intended settlement receipt fixes complete owned job/source/upload/link/event images and exact new ledger/retry identities **before** effects. Actual rows must match those expectations after application and again after the enclosing coordinator runs deferred constraints and remaining effects. A trigger result cannot redefine expected success. The receipt is bound to the same database/backend/transaction/postmaster lifetime and cannot be reused after commit. Persistence borrows computation evidence so an outer whole-transaction retry can reuse immutable staged data without manufacturing a duplicate authority proof.

Quarantine reads and derivative publication use a separate private root opened as an actual no-follow directory descriptor, with private mode and current service-owner checks. Fixed hash/UUID components, bounded manifests, exact lengths and SHA256 protect reads. The blocking I/O owner keeps its finite admission until the real closure finishes even if its async caller is dropped; stop and drain are explicit. Derivative bodies and manifests are fsynced and published with a no-replace link. A crash before SQL settlement may leave an unreferenced immutable object; a fresh worker verifies and adopts that exact object instead of overwriting it. Unknown or corrupt existing metadata fails closed. This does not broaden the available Legal-original reader into a quarantine or generic byte reader.

The aggregate scan compute/staging budget is the remaining lease minus five seconds of cleanup headroom, at most 55 seconds; the existing 30-second ClamAV and 40-second preview caps also apply. Slow inputs can fail explicitly. This closes an over-lease operation boundary rather than claiming identical B0 timing or arbitrary raw filesystem error-message parity. Full per-owner preview reads must still retain current record/purpose/audience/preservation authority and denied-access audit behavior; no such route is activated by these components.

## Unmounted development system scanner assembly

`src/composition/src/files_system_scan.rs` constructs the system transactions only from explicit `LeasedDevelopmentDatabase` configuration and the same `ConfiguredHoldingRegistry` used by Account. A reviewed binding-key map selects the physical Holding write database; a job or caller label cannot supply a pool. Assembly verifies the distinct actual Control/Holding database identities, owner/session roles, exact lease markers and complete current migration inventories. It does not create databases, migrate schemas, load an ambient environment file or accept a production database. Startup registry verification is diagnostic, not authority for a later job phase.

Each claim/preparation or final-settlement phase obtains a new non-retrying Control request lease, locks and reads its actual current Holding binding, and retains that proof through the inner Holding transaction and commit. The Holding unit alone retries a complete serializable phase on its original retryable SQLSTATE. The original Control callback never replays after that commit. Neither lease survives into file I/O, malware scanning, decoding or immutable staging. Final source receipts are checked after deferred constraints, and cross-Company prepared data is refused. This system path adds no current Person permission, purchase grant or saved-parent requirement.

Compiling `files-scan-worker` or Files `preview-provider` requires a qualified **libvips 8.18.7 development prefix**, its headers/library and transitive development metadata, plus `pkg-config` on the reviewed toolchain path. Set `PKG_CONFIG_PATH` explicitly to that prefix's `lib/pkgconfig` and the reviewed dependency metadata directories before the worker build or strict check. The current qualified prefix is an isolated Darwin ARM64 source build; it is not a repository-global path or an automatic installer. The portable root checks retain their existing feature set; the separate worker strict check and full joined six-plus-four checks remain required evidence. Missing `vips.pc` is a native prerequisite failure, not successful worker verification. There is currently no cross-host qualified-prefix resolver or pinned Linux CI bootstrap; Linux compile provisioning and codec/corpus qualification remain open and must not be inferred from the Darwin results.

The separate `files-scan-worker` Service feature assembles `LocalSanitizationStore`, the actual ClamAV adapter and the bounded Rust preview child from explicit private roots and operator-selected tools. Its root is selected by the verified Files binding. Operational admission requires the real scanner response, definition freshness and current executable profile. Shared finite admission, stop and drain retain process and I/O cleanup ownership before pools close. The default Service build does not enable the native preview feature. No scheduler, listener or worker entry point is mounted by this assembly.

Six registered disposable integration cases pass through the common runner, including configured lease/schema refusal, a live binding change, stale same-attempt reclaim, cross-Company data refusal, a real `40001` whole-phase retry and deferred-trigger after-image rollback. Four separate registered joined provider cases pass against the qualified Darwin tools and real local ClamAV 1.5.4. They prove exact retained preview bytes, actual EICAR rejection, actual decoder rejection of an admitted but corrupt PNG, binding withdrawal committed during held decoding, stale-worker refusal and cancellation cleanup. These provider cases use only disposable source/storage/database fixtures; they do not alter the installed daemon, definitions or application services.

The first joined run retained a fixture failure: the original truncated PNG was correctly refused by byte media admission before reaching the decoder. The corrected negative uses a complete PNG IHDR/IEND envelope with no image-data chunk, explicitly proves the existing admission result, and retains the same decoder-rejection assertion. No production guard, decoder tolerance, deadline or frozen 22-case preview expectation changed.

These are component and composition checks on Darwin, not a complete Files owner or production-release gate. General preview reads still require real current per-owner record/purpose/audience/preservation and purchase policies, plus retained denied-access auditing before any state/path/storage disclosure. Missing owner ports remain explicit; neither the narrow Legal original reader nor system scan authority supplies a generic preview-read grant. Linux dynamic-library/codec closure and ARM64/AMD64 corpus qualification remain separate prerequisites for the later Docker PR.
