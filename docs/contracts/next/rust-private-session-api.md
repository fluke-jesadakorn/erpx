# Private native session API component

The explicit `erpx-service/private-development-api` feature assembles a Router for fresh disposable development databases. It exposes only GET/HEAD `/api/auth/get-session` and the existing foundation health/readiness reads. It does not mount the business, credential, SSO mutation, MFA, Directory or personal-security routers. The feature-gated CLI requires `erpx-server private-api --development-config /absolute/private.json`; it validates the same configuration and databases before binding that one loopback address, and closes its pools on graceful shutdown or listener failure. Compiling the feature does not start a listener. No installed gateway, service or current Next session loader is switched. Foundation readiness remains503 and the owner migration flags remain incomplete.

`DevelopmentApiConfiguration` has a private constructor and accepts a bounded32KiB, nested deny-unknown document. File loading requires an absolute regular private file and rejects a final symlink. Configuration requires explicit Development/direct-loopback mode, a nonreserved loopback address, exact configured Account/Holding authorities, h001+h002, three distinct lease tokens and three distinct `erpx_dev_rust_<32hex>` resources. Existing leased-resource validation checks loopback5432, the test-admin role, ownership and lease metadata. There is no ambient environment discovery, fallback database, schema repair or automatic migration. Each configured pool has three connections; partial assembly failure closes the pools already opened.

The runtime-owned `verify_current_migration_inventory` compares the complete source-owned track-specific set of migration names and SHA256 receipts. It rejects missing, extra, duplicate, oversized or changed receipts, including a receipt from the wrong track. It accepts neither historical checksum predecessors nor a name-only approximation. The bounded query runs read-only READ COMMITTED under the same canonical migration advisory-lock identity used exclusively by the runner. A cooperating migration that finishes while startup waits is observed by the subsequent receipt snapshot. `StartupMigrationInventory` is a private-constructor diagnostic, without a ready or authority flag.

Assembly checks the Control track and both Holding-write tracks before constructing actual Account dependencies. `ConfiguredHoldingRegistry.verify_startup` checks the exact active Control mappings. The real Account repository receives the same immutable registry, injected clock, authentication-secret port, one shared bounded Argon2 worker and actual two-Holding invalidator. Every later Holding session read still acquires the current Control binding proof in its own canonical transaction. A startup observation cannot authorize a request or conceal a subsequent suspension or rebinding.

The Router boundary accepts exact registered Hosts and closed paths/methods, rejects forwarded authority metadata and absolute-form request authorities, and retains bounded concurrent admission and an absolute request deadline. Cookie parsing stays in the canonical Account handler, with its8192-byte aggregate cap, duplicate rejection and audience-specific opaque secrets. Responses remain private/no-store; anonymous200/null differs from a transport or authority error. Readiness503 remains available only as the foundation's explicit incomplete state.

The named server-only frontend facade is `@erpx/feature-runtime/public/server`. `createNativeSessionClient` receives explicit literal-loopback HTTP transport configuration and separate exact public HTTPS Account/Holding origins. `createNextNativeSessionReader` calls the installed Next16.4 asynchronous `headers()` for every invocation. Neither function constructs an Actor or imports a backend implementation. Only exact Host, bounded Cookie, Accept and no-cache are forwarded.

The default transport uses a fresh direct `node:http.Agent`, one connection, no keep-alive and an explicitly empty proxy configuration. It enters neither Next patched-fetch memoization nor the development HMR fetch cache. It does not mutate the global agent, follow redirects, discover proxy variables or keep an ambient cookie jar. Caller cancellation and a250..30000ms absolute deadline own the socket and response-body lifetime. The response is limited to32KiB before strict UTF-8/JSON and generated-session DTO validation. Unknown fields, mismatched user IDs, empty session IDs, malformed dates, non200 and redirects fail with closed typed errors.

The actual provider test starts only test-owned ephemeral listeners after the in-process Router has passed. Pinned Node26.11.1 imports the actual frontend adapter and sends real Account and two Holding opaque cookies to the native Router backed by three leased databases. An active ambient proxy trap receives a separate control request while the session requests bypass it without leaking cookies. The same client observes live Holding suspension, preserves Account/sibling isolation, cancels a blocked read, reaches its absolute deadline, then performs a fresh successful read after the blocker releases. A separate child-process case executes the compiled CLI with a private explicit configuration after proving the Router, checks anonymous exact-host sessions and health200/readiness503, then sends SIGTERM and verifies released listener/pools. Fixtures and listeners are drained and closed. This is a socket-level proof; Secure-cookie browser/TLS acceptance, current-page SSR integration, broader credential/business API assembly and production deployment remain pending.
