# Native Finance journal reads and manual commands

The native development component exposes GET `/api/v1/holdings/{holdingSlug}/finance/journals/{id}` through `finance_journal_read_router`. Production configuration is rejected until Finance's own release and Company acceptance ports exist. The explicit leased private development API can now mount the workspace route for configured Holdings; the shared gateway and installed services remain unchanged.

The payload's `data` is the B0 ledger detail contract: `journal`, `lines`, and `history`. Journal columns retain their snake-case names and include People-owned `created_by_name` and `posted_by_name`. Lines retain all journal-line columns plus account `code`/`name`, ordered by ordinal. Immutable draft editions retain their columns, ordered by journal version. The separate GET `/api/v1/holdings/{holdingSlug}/finance/journals/{id}/workspace` returns the B0 `journalRecordWorkspace` data in the same retained read. It adds the actual chart row; all chart/Company accounts ordered by code,id, including inactive accounts; all Company periods ordered by start_date descending,id, including closed/closing periods; active Company dimension definitions ordered by code; and active Company dimension values ordered by code. The last query preserves B0's lack of an additional active-parent-definition predicate. Reference queries do not substitute posting policy. Workflow commands, branding and the accounting list remain on existing adapters; the scoped journal drawer read is connected as described below.

Read authorization uses the actual Account/Holding opaque cookie, current configured Control binding, selected grant, Organization lineage, current IAM/People/GPO facts, Finance module admission and `finance.read`. It does not require write, approve, preparer independence, open periods or active posting accounts. Commercial access uses real `finance.accounting` History and revalidates its retained witness; an inactive current purchase may still retain History under the existing owner policy. It is never changed into NewWork/SettleExisting from a receipt shortcut.

The first admitted source scope is explicit: current primary-book, Workflow-origin-backed Finance manual/opening journals and manual-root reversal chains. Every creation/reversal receipt must match the actual Company, creator, record, operation, command-derived journal identity and result. Secondary-book and foreign-owner sources without their native current facts are denied. A source label or a caller-supplied capability cannot grant access. The source adapter runs on the caller's existing SERIALIZABLE unit and never commits, retries or obtains a second connection.

Before IAM establishes the first Holding snapshot, the coordinator acquires the participating Commercial, Workflow, Finance and People source fences. Finance locks cover headers, lines, editions, chart/account names and book relationships, including absence predicates. Positive tuple reads preserve SQLSTATE40001 for older snapshots. Private source proofs bind database, postmaster lifetime, backend and transaction; final checks retain the original source, names and purchase witnesses. No provider, external HTTP effect or long compute occurs in this unit.

People display lookup preserves the exact Company/user relationship: an unmerged Person supplies `legal_name`, regardless of active/engagement state. It does not follow aliases or synthesize a session name. Only actual absence returns `Unlinked account`; corrupt or oversized selected rows deny. Unrelated Company/user metadata is not fetched. Name lookup accepts at most the creator/poster IDs from the already-authorized journal and retains absence sources before the first snapshot.

The response's `context` is a response-only rendering snapshot produced inside the same authorization callback as `data`: original user/Holding/Company, workspace IDs/slugs, selected assignment/version/revision, original grant scope, current role/modules/permissions and expiry. The outer canonical authorizer rechecks current authority and retains its Control lease through the Holding commit. A separate session read is never combined with later owner data. The DTO has no Deserialize path and cannot reconstruct an AuthorizedWorkContext or authorize a mutation.

Both surfaces keep the exact same current read/History policy and captured account/work context; reference data is not fetched in a second request after authorization. The first read can omit CAS headers. If any context header is supplied, the complete exact company/assignment/revision/assignment-version tuple is required and checked against the retained current selection. Workspace branch/department headers are bounded path selectors, resolved through current Organization/IAM; they carry no authority. Cookies reuse the canonical8192-byte/duplicate/audience parser. Exact Host/Holding paths apply; a supplied foreign Origin is rejected. Unknown/unsupported sources receive404; closed persistence failures contain no SQL details. Responses are private/no-store without blanket CORS.

Source rows are SQL-bounded before client collection, including aggregate byte accounting and row limits. The detail admits at most10000 combined rows and2MiB of source JSON, with256KiB per row; the complete response is also counted through a non-allocating bounded serializer before final retention. Original receipt evidence has a separate aggregate4MiB limit and ancestry is limited to100 reversals. These native resource admissions are explicit limits, not a claim of unlimited legacy parity. Wire integers must be exact JavaScript-safe integers. The TypeScript and OpenAPI outputs are generated from the Rust response DTOs, with generators absent from default/release features.

The named server-only detail/workspace frontend adapter is `@erpx/feature-finance/public/server`. It calls one native owner read using one actual asynchronous Next16.4 header snapshot. It forwards only exact Host, bounded Cookie, declared workspace/CAS selectors and read/cache headers. It never performs a preliminary session query or constructs an Actor. Its explicit literal-loopback transport uses a fresh direct Node HTTP agent with empty proxy configuration, no patched fetch/HMR cache, no redirect following and no ambient cookie jar. It caps the streamed response before strict DTO/context/data validation and owns cancellation/deadline cleanup. Supplied expected context is captured before the async read; later caller mutation cannot replace it. The existing journal drawer presenter opts into this workspace reader only when `ERPX_NATIVE_FINANCE_JOURNAL_CONFIG` is explicitly configured. With no configuration it retains the existing data source. Configured invalid input, transport and context failures never fall back to that source. The real existing page context must match the native response's user, Holding, Company, workspace, role, complete CAS and module/permission sets. Expected401/403/404/context-conflict results follow the existing page error policy. Branding, purchase controls, Workflow actions and the separate full-page accounting route still use existing adapters.

A configured `DirectoryRefreshRuntime` supplies the same concrete `HoldingWorkAuthorizer` to these reads and the Finance review administration. Stale Directory observation completes outside the Control/Holding business leases, then the normal fresh authorization unit retains the current route, profile generation, session, selection and owner facts. This does not issue a new session or give a Directory snapshot acting authority. The ordinary authorizer constructor keeps its existing behavior.

Actual disposable-PostgreSQL tests cover read-only IAM, original same-unit context, B0 journal/name fields, manual/opening/reversal provenance, retained purchase History, source-writer waits, optional CAS and canonical cookie/Host/Origin denial, selected People corruption/resource limits and detached/local-mutated witnesses. Three further real Finance/LDAPS cases prove the configured Directory path returns the original workspace context, allows an independent current reviewer to post with one receipt/audit/outbox, and refuses a permission withdrawn during provider I/O with no posting effects. An actual NOWAIT check proves Finance leases are absent during that I/O. The actual pinned-Node provider starts only an owned ephemeral Finance listener after in-process Router proof. A normal Account group switch retires the original cookie; the same typed client receives401 for it, then returns owner data with the new account's exact context from a fresh cookie while the original response keeps its original account. Listener, child and transaction cleanup are checked. These are component verification receipts; owner migration and release acceptance remain incomplete.

## Explicit development assembly

`private-development-api` includes the existing `business-http` feature. Private configuration may provide `financeJournalReads: [{holdingId, companyId}]`, at most one Company per registered Holding. Missing configuration preserves session-only routing. Only the configured exact host/slug workspace GET/HEAD is admitted; journal detail and mutation routes remain closed unless a command is separately enabled as described below. The same Control and Holding leases, live registry, current authorizer and enforced Commercial catalogue govern the read. Stale Directory observation keeps the normal refusal; this assembly does not claim configured Directory refresh support.

An explicit `accountBootstrap: true` additionally requires a Finance target and mounts existing normal Account sign-in and browser SSO handlers. Its boundary admits Account sign-in POST, Holding SSO start/callback GET and Account authorization GET, preserving Origin, cookies, state, PKCE and same-Control session selection. It does not admit the other authentication/device administration routes. Omission preserves the earlier read-only boundary.

Native Account-issued child session tokens use64-character hexadecimal secrets and purpose-separated hexadecimal session digests; the retained TypeScript product-session reader requires43-character base64url tokens with plain SHA-256/base64url digests. Grant/state/PKCE hashing is a separate shared representation. `ERPX_NATIVE_ACCOUNT_SESSION_CONFIG` selects the real private native session read for existing Identity rendering/application callers, through the concrete `@erpx/native-sdk/session` transport. Only validated identity/date fields are mapped; no token or acting context is manufactured. Current Company, work selection and IAM still come from their normal database-backed application. Configured anonymous/error outcomes never retry legacy authentication. The old frontend transport export remains compatible and reexports the unchanged implementation from the shared SDK.

The development-only Cargo example `native-finance-development` accepts an absolute owner-private case directory and an explicit disposable loopback listener. Run it with `--features private-development-api` and an explicitly supplied test-admin environment. It creates three guarded leased databases, uses the real Finance/Workflow creation interface for a synthetic journal, writes private native/Next configurations and synthetic credentials, and holds them until stdin closes or Ctrl-C. Stop consumers before shutdown so lease cleanup can finish. It never installs a service, imports existing data or emits session tokens. Browser and full flow verification status is recorded in the active execution record; a passing component is not owner or release acceptance.

The bounded read flow has now passed development browser verification against the same leased databases: real credential sign-in and SSO, current database-backed work selection, the native workspace HTTP read and the rendered journal right drawer with its Cash/Sales rows. An owned read-transport outage displayed the existing record error drawer without substituting legacy journal details; restoring the transport restored the native read. A missing journal displayed the existing unavailable-record policy before the native read, so that browser case is not claimed as native404 evidence. The isolated TLS edge forwards WebSockets as well as HTTP; its initial missing upgrade forwarding was corrected in the verification fixture, without a product/authentication change. Shared public development and installed production were not switched. This is one qualified read flow; Finance owner and command migration remain incomplete.

## Native manual journal posting

The explicit private development API additionally accepts `financeJournalPosts: ["h001"]`. Targets must be a subset of configured journal-read Holdings and use the same configured Company, current Holding binding and genuine authorizer. Omission remains read-only. Only exact registered host/slug POST `/api/v1/holdings/{holdingSlug}/finance/journals/{id}/post` is admitted; reverse requires its separate opt-in below; other native writes stay closed. The enforced composition accepts protected manual/opening provenance only, including on replay; it cannot route other owner sources through a missing Flow policy. Production assembly remains unavailable.

Posting retains Finance's current permission, independent same-Person reviewer, version, period, dated Money/source and purchase checks. It also enforces the actual Workflow primary for the journal's source Company scope, using owner-qualified People, Identity and Organization facts. Saved/default primary choices, eligibility and absence/version witnesses remain current. Flow preparation follows the first replay miss and Money preparation; the route/event writes happen within the existing command ledger after its second replay check, followed by Finance effects and final source retention. A failure rolls back Flow, journal, Money, receipt, audit and outbox together. Exact replay still checks current authority/source/History but creates no additional Flow or financial effects. Terminal posting has no next staff recipient.

The Next edge and journal action use a separate server-only `ERPX_NATIVE_FINANCE_JOURNAL_POST_CONFIG`, with the same explicit configuration shape as the read transport. Read configuration alone cannot enable it. The exact POST branch forwards the original bounded body, key, cookie, workspace selectors and all four CAS fields to native authorization; it does not construct an actor or enter legacy posting on configured failure. A supplied Origin must match the Holding; the retained absent-Origin behavior is preserved. Rust-owned input/result declarations generate the SDK types and [POST OpenAPI](finance-journal-post.openapi.generated.json).

The action retains its original payload, key and full context through an uncertain result and a same-context drawer remount. A changed context cannot rebase the pending command. A valid posted receipt followed by an unavailable native readback becomes saved/readback-pending; retry then reads rather than posting again. Acknowledgement requires matching native journal/context/version and preserves any newer form edits instead of refreshing them away. Finance's app entries use their generated Next layout signatures, including the required record slot, while forwarding their existing shared layouts.

Actual disposable-PostgreSQL verification covers primary/creator-alias and malformed-primary decisions, stale context/version, late failure rollback after Flow/Finance effects, exact replay after a route change, and native readback. The browser qualification used the manual journal: genuine credentials/SSO, a real committed native POST whose reply was deliberately dropped by the owned transport, explicit retry with identical body/key hashes, and rendered native readback `posted`, version2. The actual case contained one each of the Flow event, command receipt, Money snapshot, audit and outbox event. The interface hydrated and navigated without a document reload or page errors. Opening implementation shares the enforced source scope; this browser case does not establish every journal type or command. Other owner sources, the accounting list and remaining legacy services still prevent Finance owner completion.


## Native manual-root journal reversal

The private development API separately accepts `financeJournalReversals: ["h001"]`, a subset of configured journal-read Holdings. It can be enabled without posting. Only the exact registered host/slug POST `/api/v1/holdings/{holdingSlug}/finance/journals/{id}/reverse` is admitted. Protected source evidence must identify a direct manual root; opening journals, foreign-owner sources and reversal chains are outside this bounded write scope, including replay. Default configuration and production activation remain closed.

Reversal uses current Finance read/write/approve authority and the existing period, dated Money, protected source and purchase rules. It permits the creator or original poster under the existing reversal contract. Unlike posting, it does not require a Workflow primary or HR eligibility and creates no additional Flow route/event or staff notification. The original journal transition, new posted reversal, signed Money, command receipt, audit and outbox share one transaction. Captured Money is reversed using its original valuation rather than retranslating at today's rate. Exact replay still checks current authority and protected source, returns the original two-ID receipt, and creates no additional effects.

The frontend uses independent server-only `ERPX_NATIVE_FINANCE_JOURNAL_REVERSE_CONFIG`, including its readbacks; POST configuration is not required. The request remains `{periodId, entryDate, memo?}` with no invented expected-version field. Omitted and empty memo remain distinct and null is invalid. HTTP201 returns `{reversalJournalId, reversedJournalId}`. A retained action preserves the original body, idempotency key, complete work context and form snapshot across an uncertain outcome and same-context remount. It never silently rebases a pending command onto a changed account/role/context.

After a valid receipt, retry performs native reads only. Acknowledgement requires the original journal to be reversed at the next version and the distinct posted reversal at version1 to point back to it, with both responses matching the captured context. The internal Next `reversal-workspace` branch selects the reversal transport and forwards to the existing native workspace route; it adds no new Rust read policy. Pending readback or newer form edits cannot be mistaken for a rejected transaction or refreshed away. Verification status and limitations remain in the single execution record; implementation alone is not flow, owner or release acceptance.


The bounded reversal flow passed independent source review and affected real PostgreSQL checks, including reverse-only and combined action configurations, creator reversal, exact replay/key conflict, unsupported opening source, current-context/period denials and late audit failure rollback. Its actual browser journey signed in normally, posted the draft through native HTTP, submitted the January2 reversal, lost the real committed201 response, retried the identical body/key and confirmed both native journals in the existing drawer without a document reload. Read-only database comparison against a pre-reversal snapshot proved the original Money and lines unchanged, a signed reversal at the original currency/scale/FX/fallback valuation, exactly inverted debit/credit and base lines, and one receipt/audit/outbox with zero reversal Flow events. The leased databases, listeners and transient credentials were cleaned after verification. This is a third qualified flow, not Finance owner or production acceptance.


## Manual journal creation ingress

The bounded native creation flow uses its own default-off `financeJournalCreates: ["h001"]` runtime target, a subset of read Holdings, and server-only `ERPX_NATIVE_FINANCE_JOURNAL_CREATE_CONFIG`. Read, posting or reversal configuration does not enable creation. Its public command is POST `/api/v1/holdings/{holdingSlug}/finance/journals`; the actual current Account/work context and complete CAS remain authoritative. This HTTP entry retains the existing catch-all `finance.read` gate followed by the owner's `finance.write` authorization; it adds no approval or HR eligibility requirement. The lower-level typed owner interface is not globally tightened. Input uses the existing chart, period, entry date, currency, optional FX/memo and line fields. The ingress chooses effective manual ownership, no source ID and non-opening behavior after validating the supported request profile. It does not expose opening import, editing or arbitrary foreign-owner creation.

The normalized command and deterministic `journal-{key}` identity remain inside the existing transaction ledger. The real owner preparation governs amounts, balance, chart, period, accounts and FX. New work requires current Commercial NewWork admission; only an exact retained receipt can use replay History. Draft creation does not emit a posted Money snapshot or Workflow route/event. The atomic journal/lines and receipt/audit/outbox must retain complete current source and authorization evidence; a partial fixture assertion cannot stand in for that composition.

Dimension codes and values accepted by this bounded editor profile are PostgreSQL-compatible scalar UTF-8 text, matching the current editor's actual reference-data producer. Lone UTF-16 surrogate dimensions are rejected rather than replaced silently. Original validated ordered dimension JSON is retained for command identity; the owner preparation uses its existing deterministic map. This is a stated finite producer boundary, not a claim to accept every arbitrary historical JavaScript string or a reason to extend Workflow's JSON API.

The owner-derived [create OpenAPI](finance-journal-create.openapi.generated.json) constrains201 to draft/version1. The receipt contains `id`, `number`, `status`, `version`, `debit`, `credit`, `fxRateMicros` and `baseCurrency`. The create action retains the original JSON, key, complete work context and form capture across uncertain responses. A first definitive pre-command wire refusal (`422 VALIDATION_FAILED`, `Invalid journal.`) releases the attempt while retaining the form for correction. After any earlier uncertain result, a later refusal cannot discard the original request. After a valid draft/version1 receipt, it retries only the native create-config workspace read. Navigation to the new journal follows matching manual/draft/version1 readback and current context; newer form edits are retained. Adding/removing lines explicitly marks the form edited even though those changes occur in React state. The accounting list and its reference data remain existing auxiliary services. Flow qualification is recorded only after affected real PostgreSQL and browser verification in the primary execution state; this section does not declare completion.


The bounded create flow passed the independent source review and affected PostgreSQL checks: normalized input, current selection/permissions, NewWork versus matched replay History, exact retry/key conflict, unsupported inputs, source drift, late audit rollback, native readback and independent posting. The actual browser corrected an HTML-valid exponent amount after its definitive native422, retained a valid creation through a dropped committed201 response, retried the identical key/body and navigated to the native manual draft/version1 drawer. Read-only database checks found one journal, two lines and one receipt/audit/outbox, with zero draft Money snapshots and zero creation Flow events. A fresh normal reviewer session then posted that journal through the UI/native endpoint and confirmed version2, proving its creation origin remains usable. The original create receipt and effects stayed single.

A second credential sign-in in the creator's existing browser returned `INVALID_SESSION_PROOF` during SSO. That attempt is preserved as a verification limitation and does not qualify same-browser account switching; the successful independent reviewer proof uses a fresh normal browser session. No product guard was bypassed. Owned case databases/listeners and transient credentials/cookies were cleaned. Creation is a fourth qualified bounded flow; editing, mixed-source accounting lists and remaining owner services still prevent Finance owner or production acceptance.


## Manual draft editing and receipt-linked editions

The bounded native edit ingress is POST `/api/v1/holdings/{holdingSlug}/finance/journals/{id}/edit`, independently enabled by runtime `financeJournalEdits` and server-only `ERPX_NATIVE_FINANCE_JOURNAL_EDIT_CONFIG`. Success and exact replay retain HTTP200 with `{id, status: "draft", version}`. The strict body contains chart/period/date/currency, optional memo, lines, positive current `expectedVersion` and a trimmed reason of10–2000 characters. It does not admit the create ingress's source/opening/FX fields. The current authorized editor becomes the preparer (`created_by`); posting independence and current Workflow eligibility continue to use that latest preparer.

Creation receipt metadata and a snapshot hash alone cannot authenticate an edited lineage. The selected design adds a Finance-owned append-only receipt-link table beside the existing immutable editions. A first native edit may anchor only an already-admitted unedited manual draft/version1, with zero existing editions, a positive original creation receipt and its complete locked before-image. The anchor is an admission-time baseline, not a reconstruction of the creation body from its request hash. Later editions require contiguous version/hash links to their actual retained edit receipts, Company, actor and complete snapshots. Reads, review and creation replay use the same Finance provenance interpretation so mutable current preparer identity cannot replace original creation evidence.

The writer uses the existing journal preparation for dated period, accounts, balance and FX, preserving the book/currency and original identity. Draft edits create no posted Money snapshot or Workflow route/event. Header/line replacement, immutable editions, receipt links and command receipt/audit/outbox share the existing transaction. The append occurs through existing ledger callbacks after the actual receipt is available; final retention is idempotent. New work and exact replay retain their separate Commercial admission. Existing edited rows without a genuine linked chain are not automatically adopted or backfilled. This is the current bounded implementation contract; the primary execution record retains its incomplete status until native runtime, affected PostgreSQL and browser verification close the flow.


Edit confirmation matches the unique immutable edition at the receipt's original version, editor and stored reason, while retaining the exact original request body/key. A legitimate later edit, post or reversal cannot trap an older successful attempt in perpetual readback-pending: the native-attested current head may have advanced, provided the original edition and full captured rendering context still match. Equal-version heads retain the original-editor check. Unicode reason comparison uses the trimmed well-formed storage representation only; request bytes and receipt identity remain untouched. SQL-side image/receipt budgets and canonical draft/post/reversal metadata remain enforced in the native provenance path. The first anchor retains the original receipt fingerprint from before any owner effects and refuses a changed baseline during final retention.
