# Billing Sandbox operations

The new [product/package contract](product-separation.md#commercial-packages) defines prospective Holding package grants independently of this billing model. Its store is not yet connected to live enforcement or administrator commands. This implementation does not reprice or rerate past months, add paid signup, or count product sessions as extra seats.

Historical ADR-028 Support billing remains chargeable for existing enrollments. The [original read-only pricing hypothesis](billing-pricing-hypothesis.md) uses AI cost plus 20%; the new [ADR-037](../../adr/ADR-037-sandbox-ai-gateway-and-rated-holding-billing.md) target offering uses plus 10% and requires explicit future-month assignment. Shadow rating never creates a Stripe command. A designated Sandbox test account can invoice the target offering only after a closed, complete, statement-reconciled month and reasoned Platform Admin approval.

The current target price version starts with the first active named seat at THB 499 per seat-month. There is no Holding base fee, minimum seat count, or automatic entry fee. Each paid seat-month contributes 2 decimal GB-months of original-file allowance; excess is THB 5 per GB-month. This is a Sandbox price hypothesis and creates no live storage entitlement. Optional setup or Support is a separately approved service, not an entry charge.

The read-only **Next-month seat forecast** on Holding and Platform Billing is a what-if calculator, not a rated period or invoice. It uses the next Asia/Bangkok month, the latest Control snapshot of active named seats and original-file bytes, and the closest seat-only catalog version already effective for that month (or the earliest later version if none is effective). A future-effective version is conspicuously labeled hypothetical. Users may change full-month seats and average decimal GB; no scenario is saved. AI starts unestimated. An explicit assumed ERPX-funded provider cost, including zero, adds the catalog markup and unlocks a what-if total. BYOK, current Support, extras, taxes and payment fees are excluded. Missing meters stay blank; partial or stale sources are disclosed. The calculator does not create assignments, charges, invoices, entitlements or Stripe commands.

- Customer: `/holdings/acme/settings?section=usage`. Platform: `/platform/billing`.
- Schema: control billing migrations `0009`, `0022`–`0029`, Holding write migrations `0342`–`0346`. Private evidence: `<ERPX_DATA_DIR>/files/platform-billing`, never a static asset path.
- The Billing page exposes the current active-seat count as a point-in-time operational reading. Billable seat-months require complete historical seat intervals; an unavailable monthly meter must not be filled from the current count. Measured AI requests and original-file byte-time can be shown before target-price assignment. Provider expense is shown only from verified evidence, and a final charge remains unavailable until all applicable sources and costs reconcile.
- Run the durable jobs process with the same Sandbox keys and control database as the app. The independent 30-second `billingWork` loop closes due periods, applies queued service changes, issues approved invoices, drains signed event inboxes and reconciles stale open invoices. Its successful passes update the `runtime_health` billing heartbeat, independently of other modules. Do not change the machine clock or manually close an active customer month.
- Enable `invoice.*`, `credit_note.*`, `payment_intent.*`, `setup_intent.*`, `checkout.session.completed`, `customer.subscription.*` on the test webhook. Endpoint: `/api/v1/stripe/webhook`. Persist before acknowledgment; failures retain inbox entries and retry. Stripe does the card collection retries.
- Approval requires a closed service month and an explicit cost-completeness review. THB integer satang; manual due date is seven days from finalization. Auto-pay requires saved card + consent. Withdrawal disables future automatic collection, but cannot reverse a payment already processing at Stripe.
- Optional PromptPay on manual Sandbox invoices requires `ERPX_BILLING_PROMPTPAY_SANDBOX=true` in the app and billing jobs environment, plus PromptPay enabled on the Stripe test account. Manual `send_invoice` includes card and PromptPay; `charge_automatically` remains card-only. PromptPay is customer-initiated per invoice. Keep the flag off until a real Stripe Sandbox payment acceptance run confirms account support; the deterministic fake-Stripe test proves only request shape.
- To correct unpaid issued amounts: Void, wait for Stripe confirmation, edit the released costs, mark review complete and approve again. Paid amounts are immutable; record an adjustment with an original invoice reference. Net credits require manual reviewed Stripe credit-note handling; automated refunds are outside scope.
- Jobs in `attention` are shown in Platform Billing. Retry transient failures with the existing job/Stripe keys. `IDEMPOTENCY_WINDOW_EXPIRED` intentionally refuses automated retry: locate the Stripe invoice by metadata `erpx_invoice_id`, reconcile missing local progress against its lines, and only resume after review. Do not create another invoice to resolve an ambiguous timeout.
- Evidence uploads accept signature-checked PDF/PNG/JPEG, max 5 MB, served as private attachments only to Platform billing roles. Customer URL guessing cannot access them.
- Sandbox tests use isolated database fixtures and injected clocks. No test changes the host clock or backdates the actual Holding enrollment. The sample total 925 baht is Hosting 300 + Storage 50 + provider-funded AI 75 + Standard Support 500 for a full month.

No Live keys, Live events, taxes, coupons, annual billing, automated refunds, actual access restrictions or data deletion are supported. Target Sandbox invoices alone mirror Stripe-confirmed receivable, revenue, receipt, credit and void entries to the isolated ERPX Holding test ledger; normal Finance posting remains subject to its independent approver.
