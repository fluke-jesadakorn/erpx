# Native Company purchase capability component

The Commercial Rust crate implements current package capability decisions and borrowed PostgreSQL evidence under [ADR-052](../../adr/ADR-052-rust-backend-and-domain-aligned-frontend.md). It is a component migration; billing/providers, production review composition, obligation projections, admin APIs/SSR and complete owner activation remain pending in the [migration register](../../status/rust-backend-migration.json).

The owner holds 38 versioned package definitions in `resources/packages.v1.json`. A resource adapter loads the catalogue; portable domain code validates its metadata and implements decisions without HTTP, SQLx, filesystem or environment imports. Native tests compare 9,153 decisions and 21 grant-change cases against unchanged B0 TypeScript sources executed on pinned Node 26.11.1. Included foundations, addon dependencies, expiry/draining/inactive behavior, retained historical rights and exact Company scope remain distinct. A purchase never supplies personal authority, record access or release readiness.

`CapabilityPurpose` is explicit: `NewWork`, `SettleExisting` or `History`. Expired/draining periods do not allow new work, but can retain settlement; inactivation removes current settlement. Audited retained history can still authorize the historical purchase dimension. Legal must request both its kind capability and `legal.documents` when its workflow requires them. An authorized matching receipt replay selects history; a new producer command selects new work, and a claimed existing job selects settlement. Request payloads cannot select these purposes to broaden a command.

`PackageEnforcementMode` is also mandatory: disabled, shadow or enforced. No default mode or environment fallback is embedded in the domain/reader. Inspections preserve the actual purchase decision separately from whether the explicit mode permits the operation; shadow/disabled do not turn a denied purchase into a granted personal permission. Composition owns reviewed configuration and shadow observations. Owner-specific rollout/readiness, IAM/MFA and record/preservation gates still run independently.

## Transaction evidence

`PgCompanyPurchaseReader` receives the configured Holding/Company, current catalogue and caller-owned `SERIALIZABLE` connection. It neither obtains a pool connection nor commits/retries or calls providers. The public lock helper preserves the existing writer/settlement fence order. It is not a purchase proof: ordinary writer-compatible table locks alone cannot refresh an earlier snapshot. The concrete reader also retains the per-Company advisory fence and tuple locks on current grant/history facts. A real regression establishes an earlier owner snapshot and commits an audited revocation on another backend; the reader preserves SQLSTATE `40001` for the outer unit of work to retry.

An inspection returns capability decisions, a revision and an opaque source witness. **A witness also exists for an observed denial.** Call `require_allowed()` before owner effects and on the returned revalidation result; possession of the witness alone grants nothing. The opaque token binds Holding, Company, exact capability/purpose/mode request, current catalogue/source revision, database, backend and transaction. It has no deserialization path. Prior-transaction reuse fails even on the same pooled backend.

Revalidation samples the caller's current trusted clock and checks source and temporal phases again. Mere clock ticks leave the revision stable; start, expiry and retained-right boundaries invalidate it. A source change, context mismatch or crossed boundary fails closed. Commercial's internal native revision format is opaque and is not presented as byte-identical to the previous JavaScript digest.

Twelve disposable PostgreSQL cases prove Company scope, explicit modes, audited retained history, expiry/revocation behavior, rollback, serializable retry classification and same-backend transaction fencing. They preserve the existing migration tracks and audit/history triggers; no production or existing development grant is modified. These receipts do not establish complete Legal bridge assembly, business owner migration or browser/production acceptance.

## Single-grant commands

`PgPackageGrantCommands` exposes preview/apply through a private PostgreSQL write unit. The application retains receipt-before-Company lock ordering, current authorization before receipt replay, exact request hashes, version checks, settlement obligations and dependency checks. Writes and immutable owner audit/history remain inside the caller's transaction. A final authority check precedes return; a failed enclosing unit rolls them all back. A preview creates neither a grant, receipt nor revision anchor, and applying a prior preview reruns current authority and every predicate.

`PgPackageGrantPolicy` must supply actual current permission/review leases and owner obligation sources before the first snapshot. No permissive authority or zero-obligation implementation is provided. The production composition of these sources remains pending; disposable tests label their synthetic authority/obligation tables explicitly. They prove grant/audit atomicity, historical receipt authorization, conflicting payload rejection, enclosing rollback, concurrent same-key whole-unit retry and a no-write preview followed by revoked-authority apply denial.

A separate retained-source fixture adds 243 dependency decisions and 21 byte-exact hashes from the previous application. The original 9,153-decision/21-change fixture remains unchanged. Production review/authority/obligation assembly, routes and browser acceptance are still required before this owner can replace its TypeScript runtime.

## Reviewed Company batches

The native batch application normalizes at most 100 distinct package changes, checks the exact Company revision, builds one prospective dependency set and applies every grant/audit plus one immutable batch receipt in the same caller transaction. It acquires all derived receipt identities before the Company lock. Base/addon changes are validated against the prospective set, including unchanged grants. The mandatory `PgPackageBatchReview` leases its review source before the first snapshot and verifies the exact preview before effects; no default approval is supplied. Receipt replay still requires current personal authority.

The retained Node oracle covers 43 normalized batch requests (including invalid input), byte-exact valid request hashes and 27 Company source revisions. Three real batch PostgreSQL cases prove write-free preview, atomic base/addon activation, exact-once replay, conflicting payload rejection, revoked-authority replay denial, stale revision/review rejection complete enclosing rollback and concurrent same-key whole-unit retry without duplicate grant audits. Review tables are synthetic test evidence, not production MFA or provider approval. A caller must propagate a failed command to its unit of work so all owner effects roll back.

## Receipt collation and final review retention

Package revisions also include persisted IDs outside the current catalogue. Native ordering therefore uses pinned ICU4X/CLDR48 with the captured Node26.11.1 en-US variant options, preserving stable equal comparisons and Map insertion/replacement order. No Unicode normalization or ordinal tie-breaker changes byte-distinct canonical equivalents. The additional retained-source corpus covers 841 comparisons, nine normalized request hashes, ten Company revisions and 18 actual legacy Map previews, including unknown accented/Thai/case/underscore and NFC/NFD IDs. The original three fixture files remain unchanged. Finance's existing 836 oracle cases also pass after aligning the shared ICU data with that captured runtime.

`PgPackageBatchReview::retain` is mandatory after all grant, audit and batch receipt writes. Production composition must finish deferred owner/final-source effects and recheck review expiry there, then return through final current personal authorization into the enclosing commit. Historical committed replay skips fresh review as before. The finalization regression observes all staged effects, denies at the review-expiry boundary and proves that the complete enclosing transaction rolls them back. This component does not supply a production signer, MFA lease or obligation projection.
