# Build-time module registration

This is a bounded engineering example for the incremental Rust migration. It grants no business authority, does not activate an owner, and does not replace the Field bundle acceptance checklist in the [delivery register](../../status/rust-delivery-bundles.json).

The Rust core is Shared and Runtime. The outer `erpx-service` composition validates the selected descriptors in `contracts/modules/backend-modules.json` before exposing the foundation router or private development API. Descriptors declare versioned public contracts, required version ranges and event schema versions. Unknown, missing, incompatible and duplicate registrations fail closed. External descriptors use the `external.` contract namespace and admit API/event metadata only; they cannot provide database handles, local factories or an in-process owner identity. No external plugin loader is implemented.

The default `existing-business` Cargo feature preserves the current nineteen business package dependency closure. It is a technical compatibility group, not a business owner or proof that each existing owner can be unplugged independently. Existing private-development, worker and contract features continue to require that group. The manifest tests compare the named owner versions and requirements with actual Cargo metadata. Owners outside the implemented native dependency closure remain in the migration register; they are not implicitly registered as native modules.

`--no-default-features` builds the actual server binary with only Shared/Runtime owner crates. `--no-default-features --features module-example` registers the read-only `/api/modules/example` route through the same outer router. The route declares `erpx.example.http` and `erpx.example.observed`, both version1.0.0. The example publishes metadata, not an event or a business effect. The route is absent when the feature is omitted. Health remains available; readiness stays503 because this foundation is not a migrated business backend.

The independent UI selection is `ERPX_BUILD_UI_MODULES=erpx-example`. Its finite manifest is `contracts/modules/ui-modules.json`; default selection is off. The isolated Apps builder composes `/applications/example-module` into its private snapshot only when enabled. The snapshot also generates an Apps proxy registration for that exact single-segment Applications page. The default registration list is empty; admission permits Apps GET/HEAD pages only and preserves existing host, API and session checks. The generated Next entry checks the existing current session before invoking the owner feature implementation. The feature reads the exact versioned Rust contract at the explicitly configured private loopback `ERPX_EXAMPLE_API_ORIGIN`; reserved service ports, redirects, oversized responses and incompatible metadata are rejected. There are no business writes. This route is an engineering example, not another product or a normal development gateway module switch.

Manifest, selection and implementation participate in the Apps build identity. Enabled runtime identity also includes the composer and its generated authentication wrapper. Off and on builds must each pass the existing isolated artifact verifier plus route, NFT and standalone graph inspection; source merely existing in a private snapshot is not evidence that it is consumed by the off build. Authentication and actual gateway reachability must be checked separately from direct component rendering.

```bash
cargo check --locked -p erpx-service --no-default-features --all-targets
cargo test --locked -p erpx-service --no-default-features --test module_assembly
cargo test --locked -p erpx-service --no-default-features --features module-example --test module_assembly
bun scripts/testing/ui-module-build-proof.ts
ERPX_BUILD_UI_MODULES=erpx-example bun scripts/testing/ui-module-build-proof.ts
```

Use the pinned toolchains and an isolated checkout with available disk space. The UI proof builds Apps and updates its isolated artifact output; do not run it against an output currently serving development. It does not start the backend, bootstrap a database, configure SSO or qualify a complete Dev Container. Runtime proof must use real normal authentication; no test identity replaces it.

The focused native Field write audit found no direct cross-owner mutation bypass in its qualified Field, Inventory, Finance, Support, Files, Workflow and Collaboration paths or Work/Records/source-read bridges. Composition calls public owner preparations and persistence in one transaction. Existing Inventory stock-version triggers, Support deferred projection and Collaboration Inbox effects remain explicit database dependencies. This does not prove database-level unplug isolation. Legacy TypeScript Runtime still imports business owners. Native Identity invitation activation also directly writes Workflow receipts outside the qualified existing-account Field journey; that capability must use the owner interface before its qualification. These limitations remain work, rather than evidence of all41-owner modularity.

## Field bundle dependency and withdrawal checklist

This is an implementation boundary, not evidence of a completed Field bundle. The current default `existing-business` feature enables all nineteen business packages; `business-http`, `private-development-api`, contract exporters and worker features currently imply that group. Field modules in `src/composition/src/lib.rs` are gated by `existing-business` or `business-http`, and `private_development_api.rs` assembles Field alongside other owners. The generic `business_http.rs` also combines Finance and Legal. Turning off a private target or hiding a route therefore does not demonstrate that Field or an unrelated owner was omitted from the binary.

The direct owner imports in the current `field_service*` composition and Field attachment composition cover Field Service, Identity Access, Commercial, People/Payroll, Organization, Assets, Support, Collaboration, Commerce, Inventory, Quality, Finance, Workflow and Files, alongside Shared and Runtime. The Field package itself directly depends on Shared, Runtime, Identity Access and Workflow. This is an observed import inventory, not a proven minimal transitive Cargo closure: follow each package's actual dependencies and each enabled composition path before selecting features. In particular, Finance cost and invoice paths, Files binding and status, Work/source reads, and Support/Collaboration effects are part of the qualified Field journeys; their absence cannot be replaced by an empty response or a fabricated proof. Other owner surfaces and retained TypeScript setup, initial stock, Files and Records dependencies remain separately scoped in the [Field ownership ledger](../../status/rust-delivery-bundles.json).

1. Define a Field composition feature containing the actual required owner dependencies and Field modules, and independently gate the Field HTTP, private assembly and contract exporters. Split the present mixed Finance/Legal router and mixed private bootstrap at their existing owner boundaries as necessary; do not make the Field feature silently enable `existing-business`. Preserve today's default feature and existing worker/contract behavior until their equivalent selections are explicitly wired. Calculate the transitive Cargo tree and register the exact selected descriptors and required public API/event versions; missing, duplicate and incompatible dependencies must fail before assembly.
2. Demonstrate the actual server binary with core only, Field closure enabled, and Field omitted while another supported selection remains usable. Verify route registration and absence, dependency tree, public contract compatibility and default behavior; separately verify the corresponding UI selection. Do not claim independent omission of all existing owners from these checks. Retain existing example and core evidence above rather than rerunning it without an affected dependency.
3. Preserve same-unit, owner-owned preparations, effects and currentness for Field commands, including Inventory/Commerce stock effects, Finance Money and invoice effects, Support deferred projection, Collaboration Inbox, Workflow receipt/audit/outbox and Records guards. Declare the required database triggers and projection dependencies; prove rollback, replay and current authority under the selected closure. A remote source read or Work ID is not a substitute for an atomic Records guard, and database-level unplug isolation is not yet proved.
4. Before bundle activation or merge, use the ledger to assign and fence each old route, direct/internal caller and Company-scoped command so there is one authoritative writer. Preserve receipt and replay continuity across the fence. Assign one owner for Files scan/cleanup, Inventory reservation alerts and Workflow projection, with their actual leases, retries and event ordering; retained TypeScript jobs remain active until this is proved. A Next transport selector is not a writer or job fence.
5. Complete the required Field setup, initial stock, Files lifecycle and consumer paths, and run the integrated journey and exact-candidate checks described in the delivery register. A separately retained dependency must have a single explicit owner and compatible atomic boundary; if it cannot satisfy that boundary, migrate the necessary consumer before withdrawal. This checklist does not authorize production activation or change the final all-owner migration scope.
