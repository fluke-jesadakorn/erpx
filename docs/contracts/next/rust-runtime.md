# Native runtime and transaction contract

The Rust runtime is infrastructure for the owner migration described by [ADR-052](../../adr/ADR-052-rust-backend-and-domain-aligned-frontend.md). It does not establish business readiness or replace the [production plan](../../production-plan.md). Native business routers remain unmounted until their complete authorization and behavior contracts pass.

## Composition and dependencies

`src/composition` owns package `erpx-service` and executable `erpx-server`. It assembles infrastructure and owner public adapters. `packages/server-runtime` is a library; owner adapters may depend on its public infrastructure facade, and runtime cannot depend on an owner implementation. Portable owner domain and application modules define their own ports and cannot import SQLx, Axum, runtime adapters, process configuration or filesystem APIs.

The runtime facade is `erpx_server_runtime::public::postgres`. Composition creates one shared `DatabasePool` per selected database resource and process, then passes clones or borrowed connections to owners. Clones share the underlying pool and admission gates. An owner must not create a pool for every request or obtain a new connection when participating in another owner's transaction.

`DatabaseManifest::load` requires an explicit absolute path. The version-one manifest contains Control write/read bindings and explicit resource slots. Slot names are configuration identifiers, not Company identifiers. `DatabaseBinding::HoldingWrite` and `HoldingRead` take a trusted slot identifier; the Control Holding registration and exact host decision must select that resource first. A Company request cannot choose a database URL or derive a binding name. Configuration errors and `Debug` representations exclude database URLs and passwords.

## Serializable Holding units of work

`PgUnitOfWork::run` leases one PostgreSQL connection for an attempt and opens a tracked `SERIALIZABLE` transaction. Every participating owner adapter borrows that connection. Receipts, business writes, audit and outbox effects belong to that same transaction. Owned return values cannot borrow the transaction.

An optional `SessionLock` coordinates a busy aggregate before PostgreSQL establishes its snapshot. Cloned pools share a keyed admission gate acquired before a connection is checked out, so same-key waiters cannot consume every pool connection. The PostgreSQL advisory lock is acquired before `BEGIN` and explicitly unlocked after the attempt. A cancellation or uncertain unlock discards the connection instead of returning a potentially locked session to the pool.

Only SQLSTATE `40001` and `40P01` replay the complete callback, at most four attempts with bounded backoff. Callbacks must therefore be replayable and must not perform external effects. A durable outbox carries such work after commit. The shared portable `UnitOfWork` port uses `FnMut` and an associated error type for the same reason.

Borrowed owner ports preserve persistence errors until this coordinator sees them. For example, `OrganizationReadPort` has an associated `Error: From<BusinessError>`; its SQLx adapter returns `PgTransactionError<BusinessError>`. A SQLx read failure must not be flattened into a semantic unavailable error before retry classification. `PgTransactionError::Business` failures are returned without retry.

## Retained Control authorization leases

`PgRequestLease` uses one `READ COMMITTED` Control transaction and invokes its callback once. The Identity session verifier acquires Control read locks and checks the current Account parent, device selection, principal, expiry, environment and exact Holding audience. The caller retains that lease while an inner Holding unit of work runs and commits.

The Control callback is never retried automatically. Replaying it after a successful Holding commit could duplicate already committed effects. Inner Holding serialization conflicts may retry while the Control proof remains fenced. Control mutations use their own command transaction instead of this authorization lifecycle.

`HoldingWorkContextInspector` wires this lifecycle for current selected-grant inspection. It obtains session and user identifiers from the verified Control proof, binds one configured Holding pool, and rejects an unrelated host before either pool is acquired. Its result contains current Company/branch/department lineage, assignment and published-role versions. Those facts are not effective IAM permission, HR or emergency authority, GPO evaluation, or an owner's record policy. They cannot by themselves authorize a business mutation.

## Immutable SQL migrations

The custom migration runner preserves the existing `control`, `control-read`, `holding-write` and `holding-read` tracks. It sorts migration names, hashes raw UTF-8 bytes with SHA-256 and records each committed file in `erpx_migrations`. It intentionally does not use SQLx's built-in migration table or checksum format.

One leased connection holds advisory lock `714928001` across a run. Each complete SQL file, including PL/pgSQL bodies, and its receipt commit atomically. A failed file rolls back while earlier files remain committed. Applied checksum changes fail with the track and filename. The two existing grandfather exceptions require both exact predecessor and canonical hashes and never rewrite the old receipt.

Application inspection calls only `erpx_migration_receipts()`. If that narrow function is absent while a receipt table exists, inspection fails closed instead of reading the privileged table directly. Migration roles and application roles remain distinct deployment responsibilities.

The runtime Cargo manifest declares `package.metadata.erpx.verification-roots` for the migration directory. Native source selection and fingerprints include new and deleted SQL files under that root. Other native crates may declare reviewed repository resource roots for static catalogues and fixtures; private directories and paths escaping the repository are rejected.

## Permission metadata boundary

The Identity owner holds the canonical permission catalog in `packages/server-identity_access/resources/permissions.v1.json`. Its Rust model validates the metadata and generates `packages/contracts/src/permission-catalog.generated.json` for frontend projections. Regenerate with `bun scripts/docs/generate-permission-contracts.ts` and verify with `--check`; scoped CI rejects drift. The native catalog requires an explicit current IAM permission list and never substitutes a role name.

The canonical business-role module catalog is `resources/business-role-modules.v1.json` in the same owner. `bun run contracts:work-modules` generates the client-safe literal-key projection in `packages/contracts`; `:check` verifies it in scoped CI. The 1,170 module and 378 beta-route oracle decisions were captured from the recorded Git revision before replacing the frontend table. `scripts/testing/fixtures/generate-work-admission-oracle.ts` verifies its three exact source hashes and regenerates only from that retained pure implementation. HTTP control characters are rejected as invalid destinations before admission.

## Permission-bearing work transactions

`HoldingWorkAuthorizer` is the implemented request coordinator. Its exact configured Holding host and verified Control family determine the user/session/Holding; request JSON cannot supply an actor. It starts a new Holding `SERIALIZABLE` transaction and acquires every IAM, current-selection, policy, People, Organization and beta-policy source lock before its first data snapshot. This ordering covers both updated rows and inserted denial predicates. A source lock obtained after an older serializable snapshot would not establish freshness; this coordinator does not accept a preexisting owner transaction for minting authority.

The adapter uses the immutable current PostgreSQL assignment/principal invariant functions, published IAM revisions, directory freshness and emergency elevation. People supplies minimal current person/engagement facts and Organization supplies the current HR seat through public owner ports. An active HR person without a linked login grants no permission; Identity must also prove the current principal represents that same person. Same-person aliases retain suspended aliases for independent-review denial. Manage ERPX supplies a borrowed Company beta-policy read; its remaining owner workflows are not migrated.

The portable application applies the canonical permission scope/identity rules, HR appointment rules, module admission and beta destination restrictions. It lends a non-deserializable, non-cloneable `AuthorizedWorkContext` reference with the caller connection only during the callback. The context has no public constructor. The callback may replay on Holding serialization failure, so all effects must remain in its transaction and durable outbox. After owner work, the coordinator checks expiry, re-reads current authority and rejects changed witnesses before committing. Directory, emergency, selected context, grant and session deadlines remain bounded; time-sensitive assignment/principal predicates are evaluated again. The outer Control lease is not retried after an inner commit.

This context proves permission and module admission only. Each owner must still enforce record policy, commercial entitlement, fresh MFA and independent review where required. No business HTTP router is mounted by this slice. Live directory/GPO refresh and production composition remain incomplete; serialized jobs cannot reuse this borrowed context as an authority token. The separate reviewed-invitation credential adapter reuses the current IAM evaluator without fabricating an interactive Work selection or permission-bearing context.

`PgQueuedWorkAuthorizer` owns the equivalent fresh Holding lifecycle for an original durable owner operation. A mandatory `PgQueuedWorkSourcePort` must first read and lock the owner's actual source/job/lease and return its opaque current source. Identity does not read foreign business tables or accept a serialized actor as that source. Composition binds the source's Holding/Company/creator to `QueuedWorkBinding`, then Identity reads current selected grant, principal, published role and effective permissions and checks the pinned native witnesses. The owner source and live authority are checked again after the callback. Source expiry or changed witnesses roll back the entire attempt. The coordinator does not authenticate an Account browser/device; it authorizes the original current durable operation.

`QueuedWorkBinding::from_current` produces a bounded historical snapshot from a current borrowed context. Its strict parser requires every native field, including explicitly present nullable witness fields, and rejects unknown permission fields. There is no historical-job compatibility fallback. The Identity PostgreSQL suite uses an explicitly synthetic owner source to exercise forged role/user/Company/version rejection and expired-source rollback.

The service composition binds Legal's actual opaque job source to that coordinator. With the `legal-pdf-worker` feature, `run_legal_pdf_short_transactions` prepares input in one authorized transaction, releases its leases before bounded computation, then starts a fresh authorized transaction to retain the result. Prepared and computed values carry data only; permission, source, Files and purchase witnesses must be minted locally in each transaction. Legal compares the exact current input identity, trust and running lease before recording the dated computation and completing the job. Only Legal's actual completion path can mint the private completion stamp accepted by the coordinator's final source check.

Fifteen disposable PostgreSQL composition cases cover actual Legal source binding, forbidden unstamped completion, expired-source rollback, and the split computation path. A held computation barrier proves that Control and Holding writers can commit while no worker transaction remains open; current role revocation then denies retention. The initial five component cases use explicitly synthetic record/purchase/provider ports.

`run_current_legal_pdf` now assembles the actual Legal record policy, Commercial purchase readers, PMS/Platform release reader, current Identity same-person facts, canonical Files reader and bounded local disk adapter. Its configured source acquires every participating owner source fence before the first Holding data statement. Its factory cannot be constructed publicly and paired with an unprepared source. Each phase remints local record/purchase/file proofs; no witness crosses computation. Three additional database cases exercise these real owner ports with an injected unavailable-tool outcome: current evidence is retained as indeterminate, membership/purchase/file revocations during computation block retention, and an unbuilt production release denies before computation or file audit. Development mode is explicit configuration; it does not establish an accepted production release.

The Legal facade preserves Company/branch/department visibility, confidential membership, requester ownership, editor membership, enabled/read-only policy, disposed-document and destruction denials, and distinct historical, new-work and settle-existing purchases. Active legal holds preserve evidence without denying an otherwise authorized read. Metadata remains readable after disposal; HTTP adapters must preserve the existing `LEGAL_DOCUMENT_DISPOSED` response status of 410. The narrow Company-manager rule/template preparation exception never releases a processing worker. Its source revision binds current owner data, members, documents, holds, preservation and configuration, excluding its own append-only inspection/access outputs. Five separate PostgreSQL cases prove current source locks, known-tuple serialization retry, rollback and transaction-bound witnesses.

Actual queue/claim/recovery and current provider probes now exist as unmounted components. HTTP gateway routes, a durable multi-Holding scheduler and production bootstrap remain incomplete. These component proofs do not establish owner completion or production acceptance.

## Structural JSON numbers

The shared `public::json_numbers` inbound helpers accept finite integral JSON forms such as `1`, `1.0` and `1e0`, matching the existing JavaScript integer boundary. They reject string/boolean coercions, fractions and overflow; safe signed/unsigned helpers enforce the exact JavaScript integer range. Owner types still enforce positive or nonnegative versions and other business rules. Monetary decimal-string contracts are unchanged. The pinned `serde_json` enables `float_roundtrip` so boundary forms such as the maximum safe integer followed by `.0` are parsed with correct rounding. URL query strings require a separate typed query adapter.

## Development verification

`bun run rust:test` runs all registered native unit targets through the common runner and records every observed case. Optional worker and contract-generation features are selected explicitly. A zero exit with empty, ignored or filtered cases is not a passing native receipt. `bun run rust:check`, `bun run rust:clippy` and `bun run rust:fmt` provide compilation and source checks; scoped CI also verifies generated Account TypeScript and OpenAPI contracts.

PostgreSQL suites are deliberate integration invocations, for example:

```sh
bun scripts/testing/test.ts integration --suite=shared.persistence.rust-postgres.integration
bun scripts/testing/test.ts integration --suite=shared.persistence.rust-migrations.integration
```

Configure the ignored `ERPX_TEST_ADMIN_URL` using the existing local test-administrator bootstrap. The native fixture requires `erpx_test_admin` on `127.0.0.1:5432/postgres`, `CREATEDB`, no superuser and no role-creation privilege. It creates only fresh `erpx_dev_rust_*` databases, revokes public connection access, records a unique lease, and verifies exact ownership and lease before cleanup. It never migrates or clears an existing development, production or staging database. Cancellation of the entire test process can leave a leased disposable database for explicit fixture cleanup; it does not authorize broad prefix-based deletion.

These suites prove source behavior and isolated database contracts. They are not complete owner migration, browser, provider, deployment or production acceptance.

Native provider suites are separately selected with the `provider` lane. Required provider configuration fails before Cargo starts; scanner-only providers do not inherit PostgreSQL administrator variables. Ordinary unit/integration and candidate-CI selection exclude them. The ClamAV provider is an explicit existing-daemon invocation and never authorizes starting or reconfiguring a service.


The shared concrete owner bridge now serves both signature verification and OCR. `legal-document-worker` builds OCR without enabling the PDF/CMS/OpenSSL verifier; `legal-processing-worker` explicitly enables both adapters. OCR preparation and retention use the same actual record, purchase, release, canonical Files and sealed Identity ports. The computation receives no transaction or permission witness. Current original retirement during computation blocks retention. A successful draft creates the OCR inspection, `document.ocr` access event and completed job atomically; an ordinary provider failure closes the job without an inspection or success audit. Only Legal's private settled-source stamp permits that terminal failed transition through the final coordinator check. Empty text remains a valid draft; no source chunk or independently reviewed citation is published automatically.

The Account regression now uses real native password sign-in and actual SSO children in two disposable Holdings. Normal central family sign-out completes during the computation gap, writes the two owner-local revocation fences, clears only the matching active selections, and prevents the fresh queued callback. The runtime's explicit `run_once` accepts a consumed `FnOnce`; neither its callback nor its commit is replayed after a Holding effect has committed. Eight persistence cases include callback/commit serialization errors and exact leased-development database validation.

`PgLegalProcessingMaintenance` is a separate, narrow system capability. Its mandatory policy checks Company enablement, current scheduled release, actual settle-existing kind/documents purchases and independently probed operational admission before claiming a current queued source. An opaque claim is minted only by the actual claim operation. It can close that exact live database/job/token/attempt/creator/source lease after personal authority or source rejection, with no original read, inspection, successful audit or inherited personal permission. Changed, expired, completed or fabricated leases cannot close another job.
