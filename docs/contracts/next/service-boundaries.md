# Service ownership and isolated verification

The [owner registry](../../../packages/contracts/src/ownership.json) assigns the 33 modules and shared service owners. Expense belongs to `people_payroll`; Commerce, Billing, Records, Workflow, Files, Work projections and runtime infrastructure have explicit shared ownership. The Holding database boundary remains unchanged.

## Dependency direction

Each owner has `domain/`, `application/`, `adapters/` and `public/`. Domain contains decisions and calculations. Application orchestrates typed repository, authorization, workflow, clock, identifier, file and provider ports. Neither layer imports Next.js, SQL implementations or global runtime. Native adapters and composition roots resolve those ports against the selected Holding resources.

Routes, pages, server components, workers and other owners enter through `public/`. Server components use owner queries for their view data; SQL and runtime resource acquisition belong to native adapters and composition roots. Server implementations live under `packages/server-<owner>/src/{domain,application,adapters,public}`. The legacy forwarding files have been removed after updating consumers; only `src/server/runtime/env.ts` remains for the unchanged staging bootstrap. A public path does not grant access to a private adapter. `bun run architecture:check` inspects direct and transitive portable dependencies, public boundaries, imports, re-exports, literal dynamic imports, `require()` and type imports. It also rejects direct SQL and runtime acquisition in components. The exact legacy edge register must shrink when an exception is resolved; it is not a blanket exemption for a module.

Presentation queries expose fixed typed readers, actor metadata and scalar configuration. They acquire native resources inside the owning adapter and do not return database, file-store or environment handles to pages or presentation helpers. Multiple readers in one prepared context retain the same supplied connection. The checker covers both `.ts` and `.tsx` presentation files, SQL passed to arbitrary helper calls, and public generic SQL facades; a renamed helper or query alias cannot evade the boundary. HTTP handlers and workers may compose typed native ports at their inbound boundary, while application and domain remain independent of that composition.

Pure helpers live in their owner packages and have an explicit owner in the registry. Consumers use the owner's named `public/rules/` exports; the checker follows their complete dependency graph and rejects infrastructure and ambient clock or random effects. Compatibility helpers that supply a default current date remain outside that core graph. Domain and application supply time through an injected clock.

## Shared transactions and native projections

Commands retain their original receipt identity, input hash, version guards, authorization checks, audit and outbox semantics. A supplied transaction context remains the same context when a command calls another owner. Owning native adapters produce staged effects; the initiating command executes them in the original order with its existing commit/rollback boundary. A late failure must roll back status, money, file binding, receipt, audit and outbox together. Replay does not repeat committed effects and does not waive the original current-authority checks. Existing workers with a separate durable retry journal retain that boundary after the business transaction rolls back.

Cross-owner reads use public queries or closed native projections. The owning adapter defines the relation and explicit columns; callers cannot supply a table name or SQL. Native consumers retain the original aliases, scope filters, bindings, ordering, aggregation and locking in the same provided statement. This preserves snapshots and transaction visibility. A table prefix alone does not establish business ownership: for example, People owns `finance_expenses`, Inventory owns `commerce_stock`, Quality owns `inventory_quality_*`, Brand owns `organization_brand_profiles`, and IAM owns the directory provisioning tables. Commerce owns the deterministic H003 Holding ledger tables `billing_test_finance_documents`, `billing_test_finance_entries` and `billing_test_finance_lines`; Billing owns its control projection and delegates Holding synchronization through Commerce's public interface.

## Test boundaries and evidence

The [suite manifest](../../../tests/catalogue/suite-manifest.json) records lane, owner, affected modules, fixture profile, jobs/scanner prerequisites and a required criticality reason for each unit/integration suite. Unit has no database setup. Integration/contract cases use real disposable PostgreSQL databases. Module E2E, cross-module journeys, UAT and provider verification have separate runners. Browser acceptance uses actual login and assignment selection, desktop/mobile projects and zero retries. Every case begins from its own prerequisites and retains failure evidence before cleanup.

See the [verification guide](../../testing/README.md) for selection commands and the [simulation contract](../../testing/isolated-browser-simulation.md) for ports and cohorts. `test:ci` carries critical native suites from both base and candidate, then unions impacted native suites and the fixed auth/payment browser baseline with affected E2E/journeys. Ownership and reverse imports are evaluated in both revisions. Unmapped/shared/global changes expand to all native and PR-supported browser suites. UAT and product-host suites require the manual full profile. A PR receipt identifies itself as `pr-regression` and records candidate, fingerprints, selection reasons, cases, cleanup, and deferred full suites; it cannot replace a full-candidate acceptance receipt. Required skipped or missing cases and incomplete cleanup fail verification. Live providers require their separate explicit lane.

Migration status in the registry describes the implementation boundary. Acceptance additionally requires regression against the current candidate. Dated receipts continue to describe their original source and environment.
