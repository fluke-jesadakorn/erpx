# Transitional development containers

This is a lifecycle foundation, not a finished onboarding path. TypeScript business services and jobs still run alongside the optional native Rust development paths. The production service, staging, and shared operator data are not container targets here.

The current scripts target only the owned `erpx-opensource-dev` Colima profile and an explicitly keyed `erpx-dev-${ERPX_DEV_WORKSPACE_KEY}` Compose project. Install the pinned toolchain image and initialize the owned profile first. Choose a unique `ERPX_DEV_WORKSPACE_KEY` containing the checkout identity and architecture (lowercase letters, digits and hyphens); changing it selects separate source, cache, PostgreSQL, scanner and secret volumes. Use the same key for both CLI and editor; a missing key is rejected before service actions. Existing unkeyed qualification volumes are retained and are not imported into a new workspace. Run `scripts/local/dev-container up`, then start the editor with the same key, `COMPOSE_PROJECT_NAME=erpx-dev-${ERPX_DEV_WORKSPACE_KEY}`, `COMPOSE_DISABLE_ENV_FILE=1`, and explicit `DOCKER_HOST` pointing to that profile. Check that no editor environment or local `.env` overrides the project name; the editor must attach to the same project rather than create a second PostgreSQL process over its explicit data volume. Open `.devcontainer/devcontainer.json`; the editor works directly in `/workspace/erpx` on the named Linux volume. Populate that volume with a fresh reviewed clone using contributor-owned access, never by copying ignored operator environment files, credentials, databases, or runtime data. `down` stops this project without deleting its volumes. It does not reset data.

The isolated PostgreSQL, scanner and mailbox share the workspace network namespace and publish no host ports. The generated development credentials stay in the workspace-key-specific secret volume. Each key has its own PostgreSQL data; provisioning one workspace must never rotate another workspace's role passwords. Cargo target/registry/git, Bun cache and node_modules are separate from the source volume and keyed by checkout, architecture and pinned toolchain. Next output cache persistence and a supported bind-mount alternative remain to be implemented and verified.

The intended local browser origins are exact `https://account.erpx.localhost:3443`, `https://acme.erpx.localhost:3443`, `https://northstar.erpx.localhost:3443`, and `https://erpx-internal.erpx.localhost:3443`. They are **not enabled yet**: the Holding and Account origin contracts need a separately reviewed, explicitly development-only exact-origin profile, and Caddy certificate/CA trust and resolver instructions are still needed. Do not redirect these names to the public Holding hosts or silently install a CA. The existing native development Tunnel continues to target `127.0.0.1:3100`; this container foundation neither changes that route nor binds its port.

Fresh clone bootstrap, migrations and synthetic seed, application startup, HTTPS/SSO, optional loopback hybrid PostgreSQL at 55432, port diagnostics, WSS/streaming, Next HMR and incremental Rust rebuild have not yet been demonstrated. Do not treat service readiness or configuration parsing as completion. A future full path must verify those flows and cache persistence on the same editable workspace, without importing production data or operator secrets.

## Local Linux verification prerequisites

`verification.Dockerfile` extends the pinned local development toolchain image with the PostgreSQL 18.6 client binaries from the same pinned PostgreSQL image, the CI native-worker build dependencies, HEIF tools, Poppler, age and Chromium system libraries. Debian packages are resolved at image build time, as in the hosted workflow; only the base images and language toolchains are pinned by digest/version. The image built on the owned ARM64 Linux engine; pinned tool versions, PostgreSQL client linkage and native package probes passed. AMD64 and actual browser execution remain unverified. Build only after checking the owned profile and available disk headroom. It neither starts a database/scanner nor supplies credentials.

After a reviewed source is available in an isolated Linux workspace, install its locked dependencies and provision a new private native libvips prefix with `bun scripts/testing/provision-native-worker.ts --prefix=<absolute-new-prefix>`; the script verifies its pinned source artifacts and records the actual build. Run the existing native worker export/check commands against that prefix. Install the repository-pinned Playwright Chromium and its required system dependencies in that isolated environment, then verify actual availability before browser tests. The existing real scanner socket and fresh definition volume must be wired to the test process and pass the attachment prerequisite checks; an image or socket alone is not scanner evidence. Use the guarded disposable PostgreSQL administrator from the owned service, never operator credentials or production data.

A local ARM64 Linux run is evidence for that architecture and environment, not a substitute for Ubuntu AMD64 hosted results. Record exact source, test selection, tool versions, architecture, failures and missing gates; do not describe skipped hosted checks as passed. Production acceptance, cross-architecture behavior, scanner readiness and browser compatibility remain separately unqualified until exercised.
